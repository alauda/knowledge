# Envoy Gateway setup fails: Backend is disabled, platform certificate not selectable, TLS-RSA ciphers or Wasm x509 on ACP

## Issue

Envoy Gateway is installed, and a route, listener or policy does not work:

- HTTPRoute status says `ResolvedRefs: UnsupportedValue: Failed to process route rule 0 backendRef 0: Backend is disabled in Envoy Gateway configuration.` A custom `Backend` was created so a virtual machine or another non-Service endpoint can be a route target.
- A certificate created in platform certificate management (Networking / Certificates) can be selected for an ALB but not for an Envoy Gateway HTTPS listener, even after it was assigned to all projects or namespaces were authorized.
- The platform certificate exists as a Secret in `cpaas-system` and the Gateway UI does not list it.
- Client TLS fails because the client offers only TLS-RSA cipher suites.
- An `EnvoyExtensionPolicy` Wasm module fails with `could not fetch Wasm OCI image: could not fetch manifest` and `x509: certificate signed by unknown authority`.

Related articles: "Envoy Gateway limits and questions: 64 listeners, access logs, operator install, HMAC-SM3 and migration on ACP".

## Root Cause

### Cause 1: Backend is disabled in Envoy Gateway configuration

The custom `Backend` kind (`gateway.envoyproxy.io`, kind `Backend`) is not enabled on the `EnvoyGatewayCtl` that owns this Gateway's GatewayClass; creating a `Backend` object does not turn the feature on. The switch is `spec.config.envoyGateway.extensionApis.enableBackend`. A flag on a different `EnvoyGatewayCtl` does not help. When the flag is already `true`, the error can persist until the controller is restarted, or until another configuration error on that `EnvoyGatewayCtl` is corrected.

### Cause 2: the Gateway can reference a cpaas-system Secret only through a ReferenceGrant

The Envoy Gateway certificate picker lists TLS Secrets in the Gateway namespace only. The platform certificate is synchronized to `cpaas-system` as a Secret of type `kubernetes.io/tls`. `Gateway.spec.listeners[].tls.certificateRefs` can point at a Secret in another namespace only when a `ReferenceGrant` in that namespace allows the Gateway namespace; the grant is per namespace, not per Secret name.

### Cause 3: Networking / Certificates does not attach certificates to Envoy Gateway

Certificates created in platform certificate management apply to ALB; they are not associated with Envoy Gateway or Ingress. A Gateway HTTPS listener references a Kubernetes Secret through `tls.certificateRefs`, and by default that Secret must be in the Gateway's namespace, so assigning a platform certificate to all projects does not make it selectable. **Configuration / Secrets** is the supported way to supply the certificate. This is a product scope limit, not a failed sync.

### Cause 4: TLS-RSA cipher suites are disabled by default

Envoy Gateway does not offer TLS-RSA key-exchange suites such as `TLS_RSA_WITH_AES_128_GCM_SHA256` by default, so a client that offers only those suites fails the handshake. Adding TLS-RSA suites to a `ClientTrafficPolicy` was only partly accepted: some suites were rejected by Envoy and others had no effect. No working product configuration enables them.

### Cause 5: the Wasm OCI fetch does not accept a private CA

The Wasm module is an OCI image in a registry whose certificate is signed by a CA that Envoy Gateway does not trust. Envoy Gateway does not support a custom CA for this fetch.

## Resolution

### Cause 1: Backend is disabled in Envoy Gateway configuration

Find the `EnvoyGatewayCtl` whose GatewayClass the Gateway uses, enable the flag there, and restart the Envoy Gateway controller.

> **Warning:** Restarting the `envoy-gateway` controller Deployment pauses reconciliation until the new Pod is Ready; data-plane traffic is served by the Envoy Pods and continues. Only when the HTTPRoute shows the Backend-disabled message. Save the object; setting `enableBackend` back and restarting again is the rollback.

```bash
kubectl get envoygatewayctl -A
kubectl get gateway <gateway-name> -n <gateway-namespace> -o jsonpath='{.spec.gatewayClassName}{"\n"}'
kubectl get envoygatewayctl <name> -n <namespace> -o yaml > /tmp/envoygatewayctl-before.yaml
kubectl patch envoygatewayctl <name> -n <namespace> --type merge -p '{"spec":{"config":{"envoyGateway":{"extensionApis":{"enableBackend":true}}}}}'
kubectl get deploy -A -o name | grep envoy-gateway
kubectl rollout restart deploy/<envoy-gateway-deploy> -n <envoy-gateway-namespace>
kubectl rollout status deploy/<envoy-gateway-deploy> -n <envoy-gateway-namespace>
```

Do not edit the ConfigMap or Deployment generated by `EnvoyGatewayCtl` directly. If the error remains after the restart, compare the live `EnvoyGatewayCtl` with the intended configuration and correct the field that does not match. Check that the `Backend` object and the `backendRef` group and kind match the installed CRD.

### Cause 2: the Gateway can reference a cpaas-system Secret only through a ReferenceGrant

Only when the Secret is in `cpaas-system` with type `kubernetes.io/tls`. Create the grant in `cpaas-system`, using the `ReferenceGrant` version that `kubectl api-resources | grep referencegrant` prints.

> **Warning:** The grant lets every Gateway in `<gateway-namespace>` reference any Secret in `cpaas-system`. Roll back with `kubectl delete referencegrant allow-<gateway-namespace>-secrets -n cpaas-system`; listeners that reference `cpaas-system` Secrets then fail their reference check.

```bash
kubectl get secret -n cpaas-system <certificate-secret-name> -o jsonpath='{.type}{"\n"}'
kubectl apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-<gateway-namespace>-secrets
  namespace: cpaas-system
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: Gateway
      namespace: <gateway-namespace>
  to:
    - group: ""
      kind: Secret
EOF
```

On the listener, set `tls.certificateRefs` to the Secret name with namespace `cpaas-system`. Edit the exported Gateway and apply the whole file; a listeners-only manifest drops the other listeners and `infrastructure.parametersRef`. The UI still lists only Secrets of the Gateway namespace, so this reference stays in YAML. Keeping the Secret name unchanged means a certificate renewal needs no edit.

### Cause 3: Networking / Certificates does not attach certificates to Envoy Gateway

Create a TLS Secret in the Gateway namespace (**Configuration / Secrets**, or the command below) and reference it from the listener's `tls.certificateRefs`. If the needed Secret is already the platform copy in `cpaas-system`, use Cause 2 instead of creating a second copy.

```bash
kubectl create secret tls <cert-name> -n <gateway-namespace> --key=<key-file> --cert=<cert-file>
kubectl get secret -n <gateway-namespace> <cert-name> -o jsonpath='{.type}{"\n"}'
```

### Cause 4: TLS-RSA cipher suites are disabled by default

Move the client to cipher suites that Envoy offers. RSA key exchange may also fail security compliance requirements.

### Cause 5: the Wasm OCI fetch does not accept a private CA

Host the Wasm OCI image in a registry served over HTTP or with a publicly trusted certificate, and point the `EnvoyExtensionPolicy` image reference at it.

## Diagnostic Steps

1. Read the route and Gateway status:

   ```bash
   kubectl get httproute <route-name> -n <route-namespace> -o yaml
   kubectl get gateway <gateway-name> -n <gateway-namespace> -o yaml
   kubectl get backend -A
   ```

   `Backend is disabled in Envoy Gateway configuration`: Cause 1. A missing `Backend` CRD is a different failure.

2. For certificates, compare namespaces:

   ```bash
   kubectl get secret -n <gateway-namespace> --field-selector type=kubernetes.io/tls
   kubectl get secret -n cpaas-system --field-selector type=kubernetes.io/tls
   kubectl get referencegrant -n cpaas-system
   ```

   Secret only in `cpaas-system` and no `ReferenceGrant`: Cause 2. Certificate only under Networking / Certificates: Cause 3.

3. A client cipher list with only TLS-RSA suites: Cause 4. `EnvoyExtensionPolicy` status with `certificate signed by unknown authority`: Cause 5.
