# Service Mesh tracing: Kiali trace links return 404, a workload has no data, or jaeger-prod-query crashes on ACP

## Issue

One of these tracing symptoms appears on a cluster where the mesh is installed and running:

- In ASM v2, every link from Kiali to the details of a trace opens a 404 page.
- Kiali pages for one workload show no data: Outbound Metrics show `No data available` for Request duration, Request size, Response size, gRPC received, and gRPC sent; only the TCP charts have data, and the Traces tab is empty.
- The container platform Observability tracing page shows no data and the error `There was an error quering for traces:Unknown Error` (the page text has that spelling).
- The call chain keeps showing an `unknown` request, and nobody can tell who sends it.
- After ASM v1 is deployed, Jaeger does not start and `jaeger-prod-query` in `istio-system` keeps crashing.
- After the platform log storage was switched from Elasticsearch to ClickHouse, `jaeger-prod-es-index-cleaner` in `istio-system` keeps reporting `failed to query indices and unmarshall response body`.

## Root Cause

### Cause 1: Kiali `external_url` for tracing is not set

Kiali builds trace detail links from `spec.external_services.tracing.external_url` of the Kiali custom resource. The documented tracing block (`provider: jaeger`, `use_grpc: true`, `internal_url: "http://jaeger-prod-query.istio-system:16685/jaeger"`) shows `external_url` commented out as optional. Left unset, every trace detail link returns 404. The value has the form `<platform-url>/clusters/<cluster>/istio/jaeger`.

### Cause 2: `service.istio.io/canonical-name` does not match the Deployment name

The sidecar is injected and the Service port name (for example `http-8040-8040`) lets Istio detect HTTP, yet Kiali shows no request metrics. The Pod label `service.istio.io/canonical-name` is set to the Service name instead of the Deployment name, so telemetry is reported under a name Kiali does not look up for this workload. In the Jaeger UI, selecting the service `<deployment-name>.<namespace>` returns the traces that Kiali does not show.

### Cause 3: the container platform tracing page is a separate product from Service Mesh v2 tracing

This is a product boundary, not a fault. Mesh v1 bundles Jaeger v1 with a custom tracing page; on 4.x a separate tracing feature for containers was derived from that page and released as a standalone UI plugin with its own backend and indices. Mesh v2 integrates Jaeger in the open-source way, and its traces are read in the Jaeger UI or in Kiali. When the container tracing backend is not deployed, the page's API calls `GET /clusters/<cluster>/acp/jaeger/api/services` and `.../api/spans` return `404` with response headers `via: alb` and `x-alb-err-reason: BackendError`, although the mesh Jaeger UI (instance `jaeger-prod` in `istio-system`) lists services and the `istio-tracing-<suffix>-jaeger-span-<date>` indices contain documents. This was confirmed on ACP 4.2.2.

### Cause 4: a Prometheus scrape appears as an `unknown` caller

The ztunnel or `istio-proxy` log of the destination workload shows an inbound `access connection complete` entry about once a minute from the same source address. That address belongs to a Prometheus instance scraping the mesh workloads. Those scrapes appear in the call chain as `unknown`. This is expected behavior.

### Cause 5: the ACP 4.3.0 `asm-operator` generates a 44-byte `cookie_secret`

The `jaeger-prod-query` Pod has two containers, `jaeger-query` and `oauth2-proxy`. The `oauth2-proxy` container exits with:

```text
invalid configuration: cookie_secret must be 16, 24, or 32 bytes to create an AES cipher, but is 44 bytes
```

Secret `oauth2proxy-secret` in `istio-system` is generated by ASM (Helm release `asm`, owned by `Asm/asm`). The ACP 4.3.0 `asm-operator` writes a 44-byte value, which `oauth2-proxy` rejects. This is a known issue of that package and is fixed in the ACP v4.3.1 `asm-operator` package. A plain `kubectl logs <pod> | grep error` shows nothing because the error is in the `oauth2-proxy` container.

### Cause 6: ASM v1 tracing supports only Elasticsearch

`jaeger-es-index-cleaner` is a Job that removes old Elasticsearch tracing indices (traces are kept for 7 days by default). ASM v1 tracing supports only Elasticsearch as storage, not ClickHouse. After Elasticsearch is removed, the cleaner still calls the old address, receives a portal HTML page, and cannot parse it. Log queries on ClickHouse are unaffected. ASM v2 has no `jaeger-es-index-cleaner`.

## Resolution

### Cause 1: Kiali `external_url` for tracing is not set

1. Confirm the field is empty:

   ```bash
   kubectl get kiali -A
   kubectl get kiali -n <kiali-namespace> <kiali-name> -o jsonpath='{.spec.external_services.tracing}{"\n"}'
   ```

2. Set it.

   > **Warning:** The Kiali operator restarts Kiali, so the Kiali UI is briefly unavailable. Only when trace links return 404 and `external_url` is empty. Rollback: `kubectl apply -f /tmp/kiali.bak.yaml`.

   ```bash
   kubectl get kiali -n <kiali-namespace> <kiali-name> -o yaml > /tmp/kiali.bak.yaml
   kubectl patch kiali -n <kiali-namespace> <kiali-name> --type=merge \
     -p '{"spec":{"external_services":{"tracing":{"external_url":"<platform-url>/clusters/<cluster-name>/istio/jaeger"}}}}'
   ```

   `<platform-url>` is the platform address used in the browser and `<cluster-name>` is the cluster that runs Jaeger. After Kiali is Ready, trace links should open the Jaeger trace.

### Cause 2: `service.istio.io/canonical-name` does not match the Deployment name

1. Compare the label with the Deployment name and check the sidecar and port name:

   ```bash
   kubectl -n <namespace> get pod <pod> -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'
   kubectl -n <namespace> get pod <pod> -o jsonpath='{.metadata.labels.service\.istio\.io/canonical-name}{" "}{.metadata.labels.service\.istio\.io/canonical-revision}{"\n"}'
   kubectl -n <namespace> get svc <service> -o jsonpath='{range .spec.ports[*]}{.name}{" "}{.port}{"\n"}{end}'
   ```

2. Set the label on the Pod template; a label on a running Pod is lost when it is recreated.

   > **Warning:** The workload rolls, and its telemetry is reported under the new name from then on. Only when the label differs from the Deployment name and Jaeger shows traces under `<deployment-name>.<namespace>`. Rollback: patch the previous value back.

   ```bash
   kubectl -n <namespace> patch deployment <deployment-name> --type=merge \
     -p '{"spec":{"template":{"metadata":{"labels":{"service.istio.io/canonical-name":"<deployment-name>"}}}}}'
   kubectl -n <namespace> rollout status deployment <deployment-name>
   ```

   If Kiali still reports `Pod has no Istio sidecar`, injection is the problem, not the label.

### Cause 3: the container platform tracing page is a separate product from Service Mesh v2 tracing

1. Confirm that Mesh v2 traces are stored and readable:

   ```bash
   kubectl get jaeger -n istio-system
   kubectl get pods -n istio-system | grep -E 'jaeger|kiali'
   ```

   Open the mesh Jaeger UI or the Kiali Traces tab and check that traces are listed.

2. In the browser developer tools on the tracing page, a `404` on `/acp/jaeger/api/services` or `/acp/jaeger/api/spans` with `x-alb-err-reason: BackendError` matches this cause.
3. Read Mesh v2 traces in the Jaeger UI or Kiali. No mesh change makes the container platform tracing page show Mesh v2 traces. If the Jaeger UI is also empty, this cause does not apply.

### Cause 4: a Prometheus scrape appears as an `unknown` caller

1. Map the recurring source address to a Pod:

   ```bash
   kubectl logs -n <ztunnel-namespace> <ztunnel-pod-on-the-workload-node> --tail=1000 | grep 'access connection complete' | grep '<destination-workload>'
   kubectl logs -n <namespace> <destination-pod> -c istio-proxy --tail=1000
   kubectl get pod -A -o wide | grep '<source-address>'
   ```

   Use the ztunnel log in ambient mode and the `istio-proxy` log in sidecar mode.

2. An address that resolves to a Prometheus Pod (or another scraper) is expected traffic. Stopping that scrape removes the `unknown` entry; no mesh object needs to change.

### Cause 5: the ACP 4.3.0 `asm-operator` generates a 44-byte `cookie_secret`

1. Confirm the signature:

   ```bash
   kubectl logs -n istio-system <jaeger-prod-query-pod> -c oauth2-proxy --tail=50
   kubectl get secret -n istio-system oauth2proxy-secret -o jsonpath='{.data.OAUTH2_PROXY_COOKIE_SECRET}' | base64 -d | wc -c
   ```

   A length of `44` with the log line above matches this cause.

2. Replace the `asm-operator` package and redeploy the mesh. Do not hand-edit the generated Secret.

   > **Warning:** Uninstalling the mesh removes all mesh components from the managed clusters; injection, gateways, and tracing stop until ASM v1 is deployed again. Only when the platform is 4.3.0, the log shows the 44-byte error, and a maintenance window is open. Rollback: not useful; the 4.3.0 package brings the crash back.

   1. Uninstall the mesh. If the delete gets stuck, see "Service Mesh delete is stuck on a failed to get cluster webhook denial or on pods that still have sidecar injection".
   2. On the `global` cluster, go to **Marketplace** > **Upload Packages** > **Operator**, delete the 4.3.0 `asm-operator` package, and upload the ACP v4.3.1 `asm-operator` package.
   3. Deploy ASM v1 again.

3. All Pods in `istio-system` should be Running, with `jaeger-prod-query` at `2/2` and no restarts.

### Cause 6: ASM v1 tracing supports only Elasticsearch

1. Confirm the error and the address the cleaner calls:

   ```bash
   kubectl get cronjob,job -n istio-system | grep es-index-cleaner
   kubectl logs -n istio-system <jaeger-prod-es-index-cleaner-pod> --tail=50
   kubectl get cronjob -n istio-system <es-index-cleaner-cronjob> -o jsonpath='{.spec.jobTemplate.spec.template.spec.containers[*].args}{"\n"}'
   ```

2. ClickHouse cannot replace Elasticsearch for ASM v1 tracing. Either keep an Elasticsearch backend for ASM v1 tracing, or move the mesh to ASM v2, where the cleaner does not exist and tracing uses the separate stack described in "Moving Service Mesh v2 tracing storage from Elasticsearch to OpenSearch with Jaeger v2". Moving editions means uninstalling ASM v1 and installing ASM v2; evaluate the differences in sidecar injection, gateway deployment, and the effect on Alauda AI if it uses the mesh before choosing it.
