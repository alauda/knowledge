# Host DNS changes do not reach CoreDNS: systemd-resolved, kubelet resolvConf, missing nameserver or a new upstream on ACP

## Issue

The DNS servers of the hosts were changed and Pods still resolve through the old servers, or the question is where CoreDNS gets its upstream servers. Typical reports:

- "The Corefile says `forward . /etc/resolv.conf`. Which file is that, and how does it get into CoreDNS? Is `/run/systemd/resolve/resolv.conf` used by default?"
- DNS was changed on an Ubuntu node, the `/etc/resolv.conf` inside the CoreDNS Pod still shows the old servers, and manual edits to the host file are reverted.
- Production Pods need to reach a public domain whose DNS answers change at random.
- An external DNS server has to be added to CoreDNS, and the standard steps are requested.
- A new global installation hangs at the Install Kubernetes step and the CNI plugin is never created; after the installation finally completes, the platform page keeps loading, `apollo` logs timeouts, and CoreDNS logs that no nameserver is configured.

The platform CoreDNS runs as Deployment `coredns` in `kube-system` with the ConfigMap `cpaas-coredns`. Its default server block forwards with:

```text
forward . /etc/resolv.conf {
    max_concurrent 1000
    max_fails 0
    policy sequential
}
```

For a Pod with `dnsPolicy: ClusterFirst`, a name is looked up in the Pod's own `/etc/hosts`, then in the `hosts` entries of the CoreDNS ConfigMap (cluster Service names are answered by the `kubernetes` plugin), and finally by the servers in the `/etc/resolv.conf` that the CoreDNS Pod received from the node it runs on.

## Root Cause

### Cause 1: on Ubuntu nodes, kubelet resolvConf is /run/systemd/resolve/resolv.conf and systemd-resolved reverts edits

CoreDNS does not read the node file directly. The kubelet writes each Pod's `/etc/resolv.conf` when the Pod is created; for a Pod with `dnsPolicy: Default`, which is how CoreDNS resolves its upstreams, the kubelet copies the file named by `resolvConf` in `/var/lib/kubelet/config.yaml`. (`clusterDNS` in the same file is the `kube-dns` address given to `ClusterFirst` Pods.)

In a cluster with mixed nodes, CentOS nodes had `resolvConf: /etc/resolv.conf` and Ubuntu nodes had `resolvConf: /run/systemd/resolve/resolv.conf`. On Ubuntu that file is generated by `systemd-resolved`, which rewrites it and reverts manual DNS changes, so the host change never reached CoreDNS. `systemd-resolved` is not supported with Kubernetes on these nodes: disable it and use a static resolver file. A running Pod also keeps its old file until it is recreated.

### Cause 2: a public domain whose addresses change at random

A fixed hosts record would go stale for such a domain. CoreDNS forwards names it does not own to the servers in its resolver file, which comes from the nodes it runs on (Cause 1). Once the host resolver answers the domain, Pods resolve it through CoreDNS and get the current answers, and the containers stay on cluster DNS.

### Cause 3: Install Kubernetes stalls and the platform page keeps loading, CoreDNS reports a missing nameserver

On a new ACP 4.3.2 deployment on ARM, the installer stopped at Install Kubernetes and the CNI plugin was not created. Inside the installer container `minialauda-control-plane`, CoreDNS was abnormal and logged a missing nameserver: `/etc/resolv.conf` on the installer node had no usable `nameserver` line. The same gap then appeared on the new global cluster: the masters' `/etc/resolv.conf` had no usable `nameserver`, CoreDNS stayed abnormal, the platform page kept loading, and restarting `apollo`, `archon` and `erebus` did not help.

### Cause 4: an external DNS server is added through the node resolver file

Because the default server block uses `forward . /etc/resolv.conf`, the upstream servers of CoreDNS are the `nameserver` lines of `/etc/resolv.conf` on the nodes that run CoreDNS. Adding an external DNS server therefore means adding it to that file on every node and recreating the CoreDNS Pods so the kubelet writes the new list into them. With `policy sequential`, the servers are tried in the order they are listed. The kubelet copies at most three `nameserver` entries into a Pod's resolver file, and the node scale-out precheck accepts only two.

## Resolution

### Cause 1: on Ubuntu nodes, kubelet resolvConf is /run/systemd/resolve/resolv.conf and systemd-resolved reverts edits

Only when `resolvConf` points at `/run/systemd/resolve/resolv.conf` and `systemd-resolved` is active on the node. On each Ubuntu node, back up the resolver content, stop and disable `systemd-resolved`, replace the `/etc/resolv.conf` symlink with a regular file, and put the new servers in it. On VMs, check whether cloud-init manages the file.

> **Warning:** Until the new file is in place, host processes on the node cannot resolve names, and a wrong server breaks external lookups for the node and, through CoreDNS, for Pods. Work one node at a time, and confirm each new server answers `dig @<server> <name>` first. Roll back with `cp -a /root/resolv.conf.before /etc/resolv.conf` (or `ln -sf /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf`) and `systemctl enable --now systemd-resolved`.

```bash
grep -n -E 'resolvConf|clusterDNS' /var/lib/kubelet/config.yaml
systemctl is-active systemd-resolved
ls -l /etc/resolv.conf
cat /run/systemd/resolve/resolv.conf > /root/resolv.conf.before
systemctl disable --now systemd-resolved
rm -f /etc/resolv.conf
cp /root/resolv.conf.before /etc/resolv.conf
vi /etc/resolv.conf
grep -rn -iE 'manage_resolv_conf|resolv' /etc/cloud/cloud.cfg /etc/cloud/cloud.cfg.d/ 2>/dev/null
```

`/run` is a tmpfs, so with `systemd-resolved` disabled nothing recreates `/run/systemd/resolve/resolv.conf` after a reboot, while the kubelet still needs the file it names. Either recreate that file from the node initialization script with the same content as `/etc/resolv.conf`, or point the kubelet at `/etc/resolv.conf` and restart it:

> **Warning:** The node stops reporting status briefly while the kubelet restarts; running containers keep running. Save the configuration first; restoring it and restarting again is the rollback.

```bash
cp -a /var/lib/kubelet/config.yaml /root/kubelet-config.before.yaml
sed -i 's#^resolvConf: /run/systemd/resolve/resolv.conf#resolvConf: /etc/resolv.conf#' /var/lib/kubelet/config.yaml
systemctl restart kubelet
```

Then recreate the CoreDNS Pods so they receive the new file:

> **Warning:** Lookups are briefly delayed while each replica is replaced. Only after the node files are corrected on every node that can run CoreDNS, with more than one replica Ready.

```bash
kubectl -n kube-system rollout restart deploy/coredns
kubectl -n kube-system rollout status deploy/coredns
kubectl -n kube-system exec <coredns-pod> -- cat /etc/resolv.conf
```

If `exec` is not possible, `crictl inspectp <sandbox-id> | grep -A8 -i dnsconfig` on the node lists the servers the kubelet gave the Pod. Update the node initialization script so new Ubuntu nodes are built the same way.

### Cause 2: a public domain whose addresses change at random

Make the resolver on every node that may run CoreDNS answer the domain, restart CoreDNS as in Cause 1, and test from a business Pod:

```bash
kubectl -n kube-system get pod -l k8s-app=kube-dns -o wide
dig <public-domain> +short
kubectl exec -n <namespace> <pod> -- nslookup <public-domain>
```

A name with a stable address can instead be added as a CoreDNS Host Alias; see "CoreDNS Host Alias records do not take effect because a ResourcePatch removes data hosts from cpaas-coredns on ACP".

### Cause 3: Install Kubernetes stalls and the platform page keeps loading, CoreDNS reports a missing nameserver

During installation, fix `/etc/resolv.conf` on the node that runs the installer, then restart the installer container.

> **Warning:** While `minialauda-control-plane` restarts, the installation progress page stops updating. A wrong nameserver breaks name resolution for every process on the node. Back up the file and confirm the nameserver answers from the node first; `cp -a /root/resolv.conf.before /etc/resolv.conf` is the rollback.

```bash
cp -a /etc/resolv.conf /root/resolv.conf.before
vi /etc/resolv.conf
sudo nerdctl exec minialauda-control-plane kubectl --kubeconfig /etc/kubernetes/admin.conf -n kube-system get pod -o wide | grep coredns
sudo nerdctl restart minialauda-control-plane
```

After installation, if the page keeps loading and the global CoreDNS log still reports the missing nameserver, correct `/etc/resolv.conf` on every master the same way, and recreate the CoreDNS Pods if they do not become Ready (a Pod's resolver file is written when it is created). Restarting `apollo`, `archon` or `erebus` is not the fix.

```bash
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=20
for n in <master-1> <master-2> <master-3>; do ssh $n 'hostname; grep ^nameserver /etc/resolv.conf'; done
```

### Cause 4: an external DNS server is added through the node resolver file

1. Confirm that the Corefile forwards to the node file, and that the new server answers from a node:

   ```bash
   kubectl -n kube-system get cm cpaas-coredns -o jsonpath='{.data.Corefile}{"\n"}' | grep -A5 forward
   dig @<external-dns-ip> <domain> +short
   ```

2. On every cluster node, add the server as a `nameserver` line in `/etc/resolv.conf`, in the position it should be tried.

   > **Warning:** A wrong or unreachable server delays or breaks external lookups for the node and, through CoreDNS, for all Pods. Back up the file on each node; restoring it and restarting CoreDNS again is the rollback.

   ```bash
   cp -a /etc/resolv.conf /root/resolv.conf.before
   vi /etc/resolv.conf
   ```

3. Restart CoreDNS so it loads the new upstream list (Warning in Cause 1), then test from a Pod:

   ```bash
   kubectl -n kube-system rollout restart deploy/coredns
   kubectl -n kube-system rollout status deploy/coredns
   kubectl exec -n <namespace> <pod> -- nslookup <domain>
   ```

If the server should answer only some zones, or the node file must not change, forward those zones from the Corefile instead; see "Pods cannot resolve intranet or external names: nameserver order, internal DNS server or debug container ping on ACP".

## Diagnostic Steps

1. Read which file the kubelet hands to `dnsPolicy: Default` Pods, and the CoreDNS DNS policy:

   ```bash
   grep -n -E 'resolvConf|clusterDNS' /var/lib/kubelet/config.yaml
   kubectl -n kube-system get deploy coredns -o jsonpath='{.spec.template.spec.dnsPolicy}{"\n"}'
   ```

2. On Ubuntu nodes, check whether `systemd-resolved` owns the file:

   ```bash
   systemctl is-active systemd-resolved
   ls -l /etc/resolv.conf /run/systemd/resolve/resolv.conf
   ```

3. Compare the node file with what CoreDNS received; different servers after a host change mean CoreDNS was not recreated or the kubelet copies a different file:

   ```bash
   kubectl -n kube-system exec <coredns-pod> -- cat /etc/resolv.conf
   ```

- Ubuntu node, `resolvConf` is `/run/systemd/resolve/resolv.conf`, host edits reverted: Cause 1.
- A public domain with changing answers: Cause 2.
- New installation stalls or the page keeps loading after installation, and CoreDNS reports a missing nameserver: Cause 3. If the node file exists but is empty after a node restart, see "CoreDNS fails after a node restart or lookups time out when a CoreDNS node is shut down on ACP".
- A request to add an upstream DNS server: Cause 4.
