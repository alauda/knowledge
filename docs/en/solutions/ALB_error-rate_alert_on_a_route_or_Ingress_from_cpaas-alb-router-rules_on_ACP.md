# ALB error-rate alert on a route or Ingress from cpaas-alb-router-rules on ACP

## Issue

The real-time alert page shows an `error-rate` alert from policy `cpaas-alb-router-rules` (also seen as `cpaas-lb-router-rules`, or called `alb-error-rate`). The text is `error-rate > 3%` sustained for 30 seconds (`error-rate > 3% 且持续 30 秒`), `error-rate > 5%` for 30 seconds, or `error-rate` at 100 percent. The alert names an ALB such as `global-alb2` in `cpaas-system`, and an Ingress or route such as `ingress/cpaas-system/courier-api/global-alb2`. It often clears after a few minutes.

The ALB Pods run two containers: `nginx` (access log) and `alb2` (configuration-loop log). The `alb_loop_time` alert from `cpaas-alb-rules` and other platform alerts that arrive together with these are covered in the related article.

Related article: [ALB alb_loop_time alert from cpaas-alb-rules and platform alerts raised with it on ACP](ALB_alb_loop_time_alert_from_cpaas-alb-rules_and_platform_alerts_raised_with_it_on_ACP.md).

## Root Cause

### Cause 1: the alert is the error ratio of one route, and the threshold and counted statuses differ by policy

`cpaas-alb-router-rules` watches the error ratio of each ALB route or Ingress over a 5-minute window. The "30 seconds" is how long the threshold must hold before firing, not the ratio window. The threshold and the statuses counted differ between installations:

- the threshold can be `0.03` (label `alert_indicator_threshold: "0.03"`) or 5% (the 4.1.5 `global-alb2` policy);
- the 4.1.5 expression counts all 4xx and 5xx (`status=~"[4-5].*"`); other descriptions count 5xx only.

If 4xx is counted, a wave of `499` or `404` in the access log raises the ratio. 5xx responses are either passed through from the backend, or generated by ALB (`502`, `504`) when the backend is unreachable.

A route whose 5-minute window contains a single request that the backend answered with HTTP 500 computes an error rate of 100 percent and fires once. For example, `ingress/cpaas-system/razor-api/global-alb2` showed one 100% point that did not recur, and the `razor-api` log showed sporadic `500` responses to `GET /platform/events.alauda.io/v1/...` requests. That sporadic window needs no change.

Many `cpaas-system` Ingresses firing at once (`dex`, `frontend`, `apollo`, `courier-api`, peaks about 7% to 17%) with no matching 4xx/5xx wave in the ALB `nginx` access log is not a backend fault: no action, no threshold change and no `global-alb2` restart.

### Cause 2: global-alb2 error-rate > 5% from occasional courier-api 500 responses on 4.1.5

On ACP 4.1.5 the alert is `global-alb2` `error-rate > 5%` for 30 seconds (`error-rate > 5%且持续30s`). Per rule, only `ingress/cpaas-system/courier-api/global-alb2` is elevated (maximum 14.29%), while `razor`, `frontend`, `erebus`, `dex`, `base-api` and `archon` stay at 0%. The expression is:

```promql
sum(rate(nginx_http_status{namespace=~"cpaas-system",pod=~"global-alb2-.*",status=~"[4-5].*",vmcluster="global"}[5m])) / (sum(irate(nginx_http_status{namespace=~"cpaas-system",pod=~"global-alb2-.*",vmcluster="global"}[5m])) + 0.01)
```

The 5xx come from one `GET` rule, `global-alb2-00443-<suffix>`, which matches `STARTS_WITH /platform/monitoring.alauda.io/v1beta1` and routes to Service `courier-api` port 8080. The `courier-api` log shows `500` for `GET /platform/monitoring.alauda.io/v1beta1/projects/<project>/clusters/<cluster>/namespaces/<namespace>/variables?regex=...&expr=query_result(kube_namespace_labels{})...`, and the same request in a browser returns `"message": "kube_namespace_labels should has selector namespace=<namespace>"`, `"code": 500`. A namespace-level monitoring dashboard asks for the global metric `kube_namespace_labels{}` without a namespace selector, and the permission check of that API rejects it; a query with `kube_namespace_labels{namespace="<namespace>"}` returns `200 OK`. These are normal requests, but this policy counts all 4xx and 5xx, so the occasional 500s push the ratio over 5%.

### Cause 3: error-rate spikes while the logging component is small or being scaled

`error-rate` (from `cpaas-alb-router-rules`, `source_type: "ingress"`) and `alb_loop_time` (from `cpaas-alb-rules`, for example a trigger value of `5534.00` that recovered within 30 seconds) both move, and the error-rate breakdown concentrates on the logging ingress `ingress/cpaas-system/cpaas-clickhouse/global-alb2` (maximum 61.54% over three days). At the same time `cpaas-statefulset-rules` reports CPU above 90% on the ClickHouse Pods `chi-cpaas-clickhouse-replicated-<shard>-<replica>`. The logging component's resource specification is too small; after it was scaled up, the related error rate stopped rising. The remaining fluctuation is within the supported range.

## Resolution

### Cause 1: the alert is the error ratio of one route, and the threshold and counted statuses differ by policy

1. Read the threshold from the alert text or the `alert_indicator_threshold` label, and the counted statuses from the `status=~` matcher in the rule expression:

   ```bash
   kubectl get prometheusrules.monitoring.coreos.com -A -o yaml | grep -n 'nginx_http_status'
   ```

2. Find the backend from the rule or Ingress name in the alert, and read the ALB access log and the backend log for the same minute:

   ```bash
   kubectl get rule -A | grep <rule-name>
   kubectl get rule -n <namespace> <rule-name> -o yaml | grep -A10 service
   kubectl logs -n cpaas-system <alb-pod> -c nginx --tail=500
   kubectl logs -n <namespace> deploy/<backend> --tail=200
   ```

3. Decide:
   - one request and one HTTP 500 in the window: sporadic, no change;
   - a sustained 500 in the backend log: the alert reports that backend; fix the backend, and do not raise the threshold;
   - ALB lines with `502` or `504`: ALB cannot reach the backend; check the backend Pods and Service endpoints;
   - many platform Ingresses firing with no status wave in the `nginx` log: no action.

### Cause 2: global-alb2 error-rate > 5% from occasional courier-api 500 responses on 4.1.5

1. Break the 5xx down by rule in vmui, then read the rule and the backend log:

   ```promql
   sort_desc(sum by(rule,method)(nginx_http_status{status=~"[5].*",svc_name="courier-api"}))
   ```

   ```bash
   kubectl get rule -A | grep courier-api
   kubectl get rule -n cpaas-system <global-alb2-00443-rule> -o yaml
   kubectl logs -n cpaas-system <courier-api-pod> | grep 500
   ```

   A rule on `/platform/monitoring.alauda.io/v1beta1`, and `500` lines for `.../variables?...expr=query_result(kube_namespace_labels{})` with the `should has selector namespace` body, is this signature.

2. Raise the threshold on that alert policy in the console.

   > **Warning:** A higher error-rate threshold also hides later 4xx and 5xx spikes up to the new value, including a backend that is really failing. Precondition: the window is occasional `courier-api` 500 responses on normal requests, as above, and the current threshold is written down. Rollback: set the previous threshold on the same policy.

Do not raise it when the `nginx` access log has no matching errors (no-action case in Cause 1), or when a backend keeps returning 500. A namespace-level chart that cannot see global series is this permission check, not a missing scrape: query with a namespace matcher, or use the global view.

### Cause 3: error-rate spikes while the logging component is small or being scaled

1. Compare the size and load of the logging Pods with the error-rate window:

   ```bash
   kubectl get pods -n cpaas-system -o wide | grep -i clickhouse
   kubectl top pod -n cpaas-system <chi-cpaas-clickhouse-replicated-pod>
   ```

2. Scale the logging component up through the workload or plugin that owns the `chi-cpaas-clickhouse-replicated-*` Pods.

   > **Warning:** Resizing ClickHouse restarts its replicas; log queries and writes through the affected replica pause until it is Ready. Precondition: its CPU is at the alert threshold during the error-rate window. Rollback: set the previous resources on the same object.

3. After the scale-up the related error rate stops rising. If the remaining movement stays inside the supported range, the `error-rate` and `alb_loop_time` thresholds can be raised under the same warning as Cause 2. Do not raise them while a backend still returns 500.

## Diagnostic Steps

1. Read the policy name: `cpaas-alb-router-rules` or `cpaas-lb-router-rules` with `error-rate` is this article; `cpaas-alb-rules` with `alb_loop_time` is the related article.

2. Read the threshold and `status=~` matcher from the live rule (Cause 1) instead of assuming 3%, 5% or 5xx only.

3. Break down the error ratio by Ingress:

   ```promql
   sort_desc(sum by (rule) (rate(nginx_http_status{status=~"[4-5].*"}[5m])))
   ```

   Expected: one rule dominates. A single 100% sample with one 500 in its backend log is Cause 1's sporadic window; `courier-api` with `kube_namespace_labels` 500s is Cause 2; `cpaas-clickhouse` together with ClickHouse CPU alerts is Cause 3.

4. Check that the ALB Pods did not restart and that users can reach the service:

   ```bash
   kubectl get pods -n cpaas-system -o wide | grep -E 'alb2|alb'
   ```
