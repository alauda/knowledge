# Pods fail to resolve Service names or resolve them to external addresses: search domains and ndots on ACP

## Issue

A Pod fails names that cluster DNS answers when asked directly, resolves a Service to the wrong address, or spends a long time resolving. Typical reports:

- Application logs show `Name or service not known`, `UnknownHostException` or `SearchDomainUnknownHostException` for a name like `<service>.<namespace>` (one dot) or a short Service name, while `<service>.<namespace>.svc.cluster.local` returns `NOERROR`.
- An in-cluster Service such as `mysql` starts returning an external address after someone pointed containers at an external resolver; the node resolves public names, the Pod does not unless a public resolver is written into the container.
- A task hangs for a long time at one stage with the default `dnsPolicy: ClusterFirst`, and does not hang with `dnsPolicy: Default`.

A Pod's `/etc/resolv.conf` is generated by the kubelet. With `dnsPolicy: ClusterFirst`, `nameserver` is the `kube-dns` ClusterIP, `options ndots:5` is set, and `search` lists `<namespace>.svc.cluster.local`, `svc.cluster.local`, `cluster.local`, plus the search or domain suffix of the node's own `/etc/resolv.conf`.

Related articles: "Pods cannot resolve intranet or external names: nameserver order, internal DNS server or debug container ping on ACP".

## Root Cause

### Cause 1: an expanded name returns NXDOMAIN while the FQDN returns NOERROR

With `ndots:5`, a name with fewer than five dots is tried with each search suffix before it is tried as an absolute name. When the node's `/etc/resolv.conf` has a company `domain` or `search` line, the kubelet copies it into the Pod search list. The CoreDNS log then shows `NOERROR` for `<service>.<namespace>.svc.cluster.local` and `NXDOMAIN` for expansions such as the name with the namespace suffix appended twice or with the company domain appended. Resolvers such as Netty fail the whole lookup when one expanded query returns `NXDOMAIN`, even though another expansion is the real Service. CoreDNS itself answers the FQDN quickly.

A readiness failure of one CoreDNS replica on `http://<pod-ip>:8181/ready` (`i/o timeout`) in the same window is a separate fault and does not explain these `NXDOMAIN` answers.

### Cause 2: a Service name resolves to an external address after external DNS was added to the container

Writing nameservers into a container's `/etc/resolv.conf` bypasses `kube-dns`. The remaining search list, or a search domain inherited from the node, then lets a short name (for example `mysql`) match an external zone. CoreDNS learns the node's resolvers only through `forward . /etc/resolv.conf` on the node where the CoreDNS Pod runs; a nameserver inside one container is not cluster DNS, and it is lost when the Pod is recreated.

If only some nodes have a route to the public resolver, CoreDNS Pods on the other nodes time out on external names while in-cluster names still work.

### Cause 3: the task hangs with dnsPolicy ClusterFirst and not with dnsPolicy Default

With `ClusterFirst`, every external name with fewer than five dots is first tried with each search suffix, often for both A and AAAA records, and each attempt is a round trip. An application that resolves many external names, or retries after slow answers, accumulates that delay. `dnsPolicy: Default` copies the node file, which has no cluster search list and the default `ndots:1`, so the expansions disappear. Lowering `ndots` to `1` on the workload reduces resolution time while keeping cluster DNS.

## Resolution

### Cause 1: an expanded name returns NXDOMAIN while the FQDN returns NOERROR

Only when CoreDNS shows `NOERROR` for the FQDN and `NXDOMAIN` for an expansion that repeats the namespace or appends the company domain. Apply both changes:

1. Point the application at the short Service name or at the full FQDN `<service>.<namespace>.svc.cluster.local` (a trailing dot forces an absolute query).
2. Remove the company `domain` / `search` suffix from `/etc/resolv.conf` on every node, keep the `nameserver` lines, and recreate the application Pods.

> **Warning:** Editing the node file changes resolution for host processes and for every new Pod. Copy the file on each node first; restoring it and recreating the Pods is the rollback. In-cluster Service names keep working through `kube-dns`.

```bash
cp -a /etc/resolv.conf /root/resolv.conf.before
vi /etc/resolv.conf          # delete only the domain or search token with the company suffix
kubectl delete pod -n <namespace> <pod>
kubectl exec -n <namespace> <new-pod> -- cat /etc/resolv.conf
```

New Pods should list `search <namespace>.svc.cluster.local svc.cluster.local cluster.local` without the company domain. See also "Platform UI stuck loading or DevOps errors from Service name timeouts caused by node search domains on ACP".

### Cause 2: a Service name resolves to an external address after external DNS was added to the container

Fix the nodes, not the container. Remove the extra search domain from `/etc/resolv.conf` on all nodes; on the nodes that run CoreDNS, put the resolver that answers public names first. Restart CoreDNS so it re-reads the file, then recreate the test Pod.

> **Warning:** Cluster lookups stall briefly while CoreDNS restarts, and recreated application Pods drop their connections. Confirm the first nameserver answers every zone you need and save `/etc/resolv.conf` first; restoring it and restarting CoreDNS again is the rollback.

```bash
cp -a /etc/resolv.conf /root/resolv.conf.before
kubectl -n kube-system rollout restart deploy/coredns
kubectl -n kube-system rollout status deploy/coredns
kubectl delete pod -n <namespace> <test-pod>
kubectl exec -n <namespace> <new-test-pod> -- nslookup kubernetes.default
kubectl exec -n <namespace> <new-test-pod> -- nslookup <external-name>
```

If public resolution works only on some nodes, keep `/etc/resolv.conf` identical on all nodes and schedule the Pods that need the public network onto the nodes that have the route (taints on the other nodes, plus a matching toleration and node affinity on those workloads). For one external name with a fixed address, add a CoreDNS Host Alias instead of a container entry; see "CoreDNS Host Alias records do not take effect because a ResourcePatch removes data hosts from cpaas-coredns on ACP".

### Cause 3: the task hangs with dnsPolicy ClusterFirst and not with dnsPolicy Default

Keep `dnsPolicy: ClusterFirst` and set `ndots` to `1` in the workload's `dnsConfig`:

```yaml
spec:
  template:
    spec:
      dnsPolicy: ClusterFirst
      dnsConfig:
        options:
          - name: ndots
            value: "1"
```

> **Warning:** Patching the Pod template rolls the workload. With `ndots:1`, a name such as `<service>.<namespace>` is tried as an absolute name first, so the application should use short names or full FQDNs. Save the Deployment; applying the saved copy is the rollback.

```bash
kubectl -n <namespace> get deployment <deployment> -o yaml > /tmp/<deployment>.before.yaml
kubectl -n <namespace> patch deployment <deployment> --type=strategic \
  -p '{"spec":{"template":{"spec":{"dnsConfig":{"options":[{"name":"ndots","value":"1"}]}}}}}'
kubectl -n <namespace> rollout status deployment <deployment>
kubectl exec -n <namespace> <new-pod> -- cat /etc/resolv.conf
```

The new Pod shows `options ndots:1` with the same `nameserver` and `search` lines. The same change on a platform component is described in "ArgoCD repo-server DNS lookups leak upstream because of pod ndots:5 search expansion".

## Diagnostic Steps

1. Compare the node file, the Pod file, and one absolute query:

   ```bash
   cat /etc/resolv.conf
   kubectl exec -n <namespace> <pod> -- cat /etc/resolv.conf
   kubectl exec -n <namespace> <pod> -- nslookup <service>
   kubectl exec -n <namespace> <pod> -- nslookup <service>.<namespace>.svc.cluster.local
   ```

2. Turn on CoreDNS query logging if needed (add `log` to the server block of `cpaas-coredns`; it reloads without a restart) and read the answers:

   ```bash
   kubectl -n kube-system edit cm cpaas-coredns
   kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
   ```

3. Map the result:

   - FQDN `NOERROR`, expanded name `NXDOMAIN`, company domain in the Pod search list: Cause 1.
   - Short Service name returns an off-cluster address and the container's `/etc/resolv.conf` was edited: Cause 2.
   - Hang with `ClusterFirst`, none with `dnsPolicy: Default`, `options ndots:5` in the Pod: Cause 3.

Read the cause from the CoreDNS log rather than from a monitoring chart before changing resolvers.
