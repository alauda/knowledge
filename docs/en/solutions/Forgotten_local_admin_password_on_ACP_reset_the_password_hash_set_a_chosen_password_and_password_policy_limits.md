# Forgotten local admin password on ACP: reset the password hash, set a chosen password, and password policy limits

## Issue

One of the following is needed for a local (not LDAP) platform account:

- The console password set at installation, or the platform `admin` (for example `admin@cpaas.io`) password, was forgotten and must be reset, and user management cannot show the old password.
- A backend password change must set a specific new password instead of the default.
- Users are being copied to a new platform from a backup, and the question is whether their passwords come along.
- A security review asks which algorithm protects local user passwords, or an audit list asks for maximum password age, password history, and lockout after failed logins.

Related articles: "kubectl returns the server has asked for the client to provide credentials after ac login, or ac login fails, on ACP" covers the CLI and API tokens. "ACP console session survives cookie deletion or a browser close, or the login page shows the previous account" covers browser sessions. An LDAP user's password is changed in the directory, not on the platform.

## Root Cause

### Cause 1: the local credential is the `hash` of a `password` object

A local account's credential is the `hash` field of a `password` object in `cpaas-system` on the `global` cluster. The platform cannot display the original password. Replacing the hash with the known default hash makes the password `P@ssw0rd`; the user then sets a new password from the profile page. Sometimes the first login after the patch is still rejected until Dex reloads.

### Cause 2: local passwords are stored as PBKDF2 hashes, so a plaintext value cannot be written

To set a chosen password from the backend, a plaintext password cannot be put into the `password` object. A hash of the chosen password has to be generated by the platform itself, for example by creating a temporary local account with that password and reusing its hash.

### Cause 3: a User backup does not contain the local password

An `auth.alauda.io/v1` User object has no password field. Exports such as `users.yaml` and `userbindings.json` restore identities and role bindings, not local passwords. There is no backup and restore for local passwords; each one has to be set again on the new platform.

### Cause 4: local user passwords use pbkdf2

Local user passwords are stored with the pbkdf2 algorithm; the default hash of Cause 1 is a pbkdf2 hash of `P@ssw0rd`. The RSA public key that the console front end uses to encrypt the password in the login request is a different topic. When the question does not say which one is meant, ask.

### Cause 5: the user password settings do not cover every audit item, and lockout applies to local users

The platform user password settings do not provide a maximum password age of three months, a reuse limit of five generations, or lockout after five failures. A configured lockout ("lock the account for five minutes after five wrong passwords") applies to local users; LDAP users are not locked by it, so a test with an LDAP account shows no lockout.

## Resolution

### Cause 1: the local credential is the `hash` of a `password` object

1. On the `global` cluster, find the `password` object of the account and back it up:

   ```bash
   kubectl get password -n cpaas-system -o=custom-columns=Name:.metadata.name,Username:.username,Email:.email
   kubectl get user -n cpaas-system | grep admin
   kubectl get password -n cpaas-system <password-resource-name> -o yaml > /tmp/password.bak.yaml
   ```

   Continue only when the row's username is the local account to reset.

2. Replace the hash with the default hash.

   > **Warning:** The account's password becomes `P@ssw0rd` until it is changed; anyone who can open the console can log in as that user in the meantime. Only for a local account whose password is forgotten. Rollback: `kubectl apply -f /tmp/password.bak.yaml` restores the previous hash (restart Dex again if it was restarted).

   ```bash
   kubectl patch password -n cpaas-system <password-resource-name> --type='json' -p='[{"op": "replace", "path": "/hash", "value":"UEJLREYyOjgrNDgzZ0QyQmJObXZXbWp6eVBVQUNNdXMyVTRqS2ZmRFlKdnZ0ZXRUMGc9OjFiTHhEMDVGeDJwWEthekF3bzBWb0E9PQ=="}]'
   ```

3. Log in with `P@ssw0rd`. If the password is still rejected, restart Dex once and retry. On 4.x Dex runs inside `apollo`; on a cluster with a separate `dex` Deployment, restart that one.

   > **Warning:** Login is interrupted until the Pod is Ready. Only when the patch succeeded and the first login was rejected. Rollback: not needed.

   ```bash
   kubectl get deploy -n cpaas-system | grep -Ei 'apollo|^dex'
   kubectl -n cpaas-system rollout restart deploy/<apollo-or-dex>
   ```

4. Open the personal information page from the upper right corner and set a new password with the pencil icon next to the password.

### Cause 2: local passwords are stored as PBKDF2 hashes, so a plaintext value cannot be written

1. On a platform that is accessible, create a temporary local account with the desired password and read its hash:

   ```bash
   kubectl get password -n cpaas-system -o=custom-columns=Name:.metadata.name,Username:.username,Email:.email
   kubectl get password -n cpaas-system <temporary-account-password-name> -o jsonpath='{.hash}{"\n"}'
   ```

2. Write that hash into the target account.

   > **Warning:** The target account's password becomes the temporary account's password. Only for a local account, with its `password` object identified as in Cause 1 and backed up. Rollback: `kubectl apply -f /tmp/password.bak.yaml`.

   ```bash
   kubectl get password -n cpaas-system <target-password-name> -o yaml > /tmp/password.bak.yaml
   kubectl patch password -n cpaas-system <target-password-name> --type='json' -p='[{"op": "replace", "path": "/hash", "value":"<hash-from-the-temporary-account>"}]'
   ```

3. Log in with the chosen password (restart Dex as in Cause 1 if it is rejected), then delete the temporary account. This method has not been verified as widely as the default-hash reset in Cause 1; if it fails, use Cause 1 and change the password from the profile page.

### Cause 3: a User backup does not contain the local password

Export identities and role bindings the usual way if that is how users are recreated, and plan to set every local password again on the new platform. Copying `password` hashes forward is not a supported restore.

### Cause 4: local user passwords use pbkdf2

Answer that local user passwords use pbkdf2. No change is needed.

### Cause 5: the user password settings do not cover every audit item, and lockout applies to local users

1. Read the policy actually configured on the `global` cluster for your version:

   ```bash
   kubectl get userpolicies -A
   kubectl get userpolicies -A -o yaml | grep -A40 'name: user-security-policy'
   ```

2. Report to the audit that a three-month maximum age, a five-generation reuse limit, and lockout after five failures are not provided by the user password settings, unless the policy object of your version shows them.
3. Test a configured lockout with a local user. An LDAP user not being locked is expected and is not a fault.

## Diagnostic Steps

```bash
kubectl get password -n cpaas-system -o=custom-columns=Name:.metadata.name,Username:.username,Email:.email
kubectl get user -n cpaas-system | grep <username>
```

| What you see | Cause |
| --- | --- |
| Local account, password forgotten, console login rejected | 1 |
| Reset must set a specific password instead of `P@ssw0rd` | 2 |
| Users restored from a backup cannot log in with their old passwords | 3 |
| Question about the algorithm that protects local passwords | 4 |
| Audit asks for password age, history, or lockout; LDAP user not locked | 5 |
| The account is an LDAP user | Reset the password in the directory |
