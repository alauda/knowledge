# PXC slow-query ClickHouse restarts, fills its disk, or its LoadBalancer blocks an upgrade on ACP

## Issue

The ClickHouse that stores MySQL PXC slow-query logs (Pods `chi-pxc-ck-slowsql-*` or `chi-pxc-ckslowsql`, Service `clickhouse-pxc-ck`, usually in `cpaas-system`) shows one of these:

- The slow-query component restarts again and again; events on `chi-pxc-ck-slowsql-cluster` or `chi-pxc-ckslowsql` show the container exiting and coming back (Cause 1).
- Slow query has to be turned off and `chi-pxc-ckslowsql` removed on ACP 3.10 (Cause 2).
- Before a platform upgrade, the pre-check stops on a MetalLB Service: `clickhouse-pxc-ck` in `cpaas-system` is of type `LoadBalancer` (Cause 3).
- The ClickHouse container of `chi-pxc-ck-slowsql-cluster-0-0-0` sits at about 80 to 90 percent memory with no Pod events (Cause 4).
- The `pxc-ck-slowsql-cluster` Pod takes a lot of storage (for example 60G), most of it in `value.bin` files (Cause 5).

`chi-pxc-ck-slowsql-cluster` collects slow-query logs for MySQL PXC instances. Raising memory, uninstalling the feature, and changing the Service type solve different problems; deleting the PVC belongs only to the uninstall.

A ClickHouse instance that a user created in an application namespace (Pods named `chi-<chi-name>-<cluster>-<shard>-<replica>-0`) is a different workload. The 2Gi and 4Gi values below come from the slow-query component and do not size such an instance; the general way to change ClickHouse operator memory is in the Cause 1 resolution, steps 3 and 4.

## Root Cause

### Cause 1: chi-pxc-ck-slowsql-cluster is OOMKilled with a 2Gi memory limit

The container's last termination reason is `OOMKilled`. The memory limit of the slow-query ClickHouse container was 2Gi (also shown as 2G). The process is killed whenever it crosses that limit, so the Pod keeps restarting. Raising the limit to 4Gi stops the restarts. If slow query is not used, the component can be removed instead (Cause 2).

### Cause 2: Slow query has to be uninstalled on ACP 3.10

This is a removal procedure, not a crash. On 3.10, uninstalling the ClickHouse operator also deletes its `csv` and `subs`. The instance is then stopped by setting the ClickHouse replica count to 0 and deleting the matching PVC.

### Cause 3: Service clickhouse-pxc-ck is of type LoadBalancer and the upgrade pre-check fails

The pre-upgrade checklist reports a MetalLB LoadBalancer for Service `clickhouse-pxc-ck` in `cpaas-system`. The slow-query ClickHouse Service does not need an external address. Changing the Service type to `ClusterIP` lets the pre-check continue.

### Cause 4: Memory stays near 80 to 90 percent and no data service is in use

`chi-pxc-ck-slowsql-cluster-0-0-0` shows ClickHouse memory around 80 to 90 percent, with no Pod events, so this is not the OOM restart of Cause 1. On ACP 4.1.5, a platform with no Data Services page has no PXC or MGR instances to manage, so the Pod is not serving any database. No further reason for the memory level is known. Scaling the workload to 0 removes the memory use from the node. This is not the 3.10 uninstall: no operator CSV is removed and the PVC is kept.

### Cause 5: Storage keeps growing, mostly value.bin files

`value.bin` is a ClickHouse table data file (a column file of a table part); here it holds the historical slow-query data. Before ACP 3.14, the ClickHouse used by PXC could not be configured to clean up slow-query and ClickHouse logs periodically, so storage use only grows. On 3.14, the fix is to adjust the data retention time of the ClickHouse used by PXC, as described in the platform documentation of that name for your version.

## Resolution

### Cause 1: chi-pxc-ck-slowsql-cluster is OOMKilled with a 2Gi memory limit

1. Confirm the last termination reason is `OOMKilled` (exit code `137`) and that the limit is 2Gi. Note the container name that owns the limit.

```bash
kubectl get pod -n <namespace> <slowsql-pod> \
  -o jsonpath='{range .status.containerStatuses[*]}{.name}{" exit="}{.lastState.terminated.exitCode}{" reason="}{.lastState.terminated.reason}{"\n"}{end}'
kubectl get pod -n <namespace> <slowsql-pod> \
  -o jsonpath='{range .spec.containers[*]}{.name}{" limit="}{.resources.limits.memory}{"\n"}{end}'
```

2. Set that container's memory limit to 4Gi on the object that controls the Pod. When the ClickHouse operator owns the StatefulSet, a change made only on the StatefulSet is reverted, so change the operator's resource (steps 3 and 4). Edit the StatefulSet directly only when nothing owns it (step 5).

3. Find out which object owns the StatefulSet. Pods and StatefulSets named `chi-...` are normally generated by the ClickHouse operator from a `ClickHouseInstallation` (short name `chi`).

```bash
kubectl get sts -n <namespace> <slowsql-sts> \
  -o jsonpath='{range .metadata.ownerReferences[*]}{.kind}{" "}{.name}{"\n"}{end}'
kubectl get chi -A
```

4. If the owner is a `ClickHouseInstallation`, edit the memory of the container in its pod template. Use the template name and container name the resource already has, and change nothing else.

> **Warning:** Saving the `ClickHouseInstallation` makes the operator roll the ClickHouse Pod, and slow-query reads fail until it is Ready again; MySQL itself keeps running. Do this only when `OOMKilled` is confirmed on the ClickHouse container, and only when the node has room for the new size, otherwise the Pod stays Pending. Save the resource first (`kubectl get chi -n <namespace> <chi-name> -o yaml > chi-backup.yaml`). Roll back by setting the same fields to their previous values.

```bash
kubectl -n <namespace> edit chi <chi-name>
```

```yaml
spec:
  templates:
    podTemplates:
      - name: <pod-template-name>
        spec:
          containers:
            - name: <container>
              resources:
                limits:
                  memory: 4Gi
```

Optionally, set `spec.configuration.settings.max_server_memory_usage` (in bytes) below the container memory limit, with the memory request and limit at the same value. That caps ClickHouse's own memory use under the limit; it has fixed OOM on user ClickHouse instances, and the slow-query 2Gi-to-4Gi fix did not need it.

5. If the StatefulSet has no `ClickHouseInstallation` owner, set the limit on the StatefulSet.

> **Warning:** Changing the limit rolls the slow-query Pod and drops in-flight queries to it; MySQL itself keeps running. Only when `OOMKilled` with a 2Gi limit is confirmed and the node has 4Gi free. Do not scale the StatefulSet to 0 or delete its PVC for an OOM. Roll back by setting the limit to 2Gi again.

```bash
kubectl set resources -n <namespace> sts/<slowsql-sts> -c <container> --limits=memory=4Gi
```

### Cause 2: Slow query has to be uninstalled on ACP 3.10

1. Find the ClickHouse operator objects that back `chi-pxc-ckslowsql` or `pxc-ck`, then uninstall the operator from the operator catalog. On 3.10 the uninstall deletes the operator `csv` and `subs`.

```bash
kubectl get csv,sub -A | grep -Ei 'clickhouse|pxc-ck|ckslow'
```

2. Read the slow-query PVC name from the Pod while it still exists. MySQL member PVCs use the instance name and `pxc-<ordinal>`; the slow-query PVC name contains `ck` or `slowsql`.

```bash
kubectl get pod -n <namespace> <slowsql-pod> \
  -o jsonpath='{range .spec.volumes[*]}{.persistentVolumeClaim.claimName}{"\n"}{end}'
```

3. Set the ClickHouse replica count to 0 and delete that PVC.

> **Warning:** Replica count 0 stops slow-query collection, and deleting the PVC permanently deletes the stored slow-query logs. Do this only when the goal is to remove the feature, not as an OOM fix. There is no rollback for the deleted PVC; a later install starts empty.

```bash
kubectl scale -n <namespace> sts/<slowsql-sts> --replicas=0
kubectl delete pvc -n <namespace> <slowsql-pvc>
```

### Cause 3: Service clickhouse-pxc-ck is of type LoadBalancer and the upgrade pre-check fails

> **Warning:** Changing `clickhouse-pxc-ck` from `LoadBalancer` to `ClusterIP` removes the external address MetalLB published for it, and clients outside the cluster that used it will fail. Do it only when the upgrade pre-check names this Service and nothing outside the cluster needs the slow-query address. Roll back by re-applying the saved YAML.

```bash
kubectl get svc clickhouse-pxc-ck -n cpaas-system -o yaml > clickhouse-svc-backup.yaml
kubectl patch svc clickhouse-pxc-ck -n cpaas-system --type merge -p '{"spec":{"type":"ClusterIP"}}'
kubectl get svc clickhouse-pxc-ck -n cpaas-system -o jsonpath='{.spec.type}{"\n"}'
kubectl get endpoints clickhouse-pxc-ck -n cpaas-system -o wide
```

`spec.type` should be `ClusterIP`, and the endpoints should still list the slow-query Pod addresses if the Pod is running. Then rerun the pre-check.

### Cause 4: Memory stays near 80 to 90 percent and no data service is in use

1. Confirm the Pod is the slow-query store, memory is high without `OOMKilled`, and no PXC or MGR instance needs those logs:

```bash
kubectl get pods -A | grep -E 'chi-pxc-ck-slowsql|pxc-|mysql-'
kubectl get mysql -A
kubectl top pod -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0
kubectl get pod -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 \
  -o jsonpath='{.metadata.ownerReferences[*].kind}{" "}{.metadata.ownerReferences[*].name}{"\n"}'
```

2. Scale the owning workload to 0.

> **Warning:** Replica count 0 stops PXC slow-query collection. Do it only when memory stays high on `chi-pxc-ck-slowsql-cluster` and no data service, PXC, or MGR instance is in use. The PVC is kept. Scale back to the previous replica count to undo it. If a controller creates the Pod again, set the replica count to 0 on that owner object instead.

```bash
kubectl scale -n <namespace> sts/<statefulset-name> --replicas=0
```

### Cause 5: Storage keeps growing, mostly value.bin files

1. Confirm which tables hold the space. Add `--user` and `--password` to `clickhouse-client` if the server requires them.

```bash
kubectl exec -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 -- du -sh /var/lib/clickhouse
kubectl exec -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 -- clickhouse-client --query \
  "SELECT database, table, formatReadableSize(sum(bytes_on_disk)) AS size, sum(rows) AS rows FROM system.parts WHERE active GROUP BY database, table ORDER BY sum(bytes_on_disk) DESC LIMIT 20"
```

2. Adjust the retention time of the slow-query data as the platform documentation on the data retention time of the ClickHouse used by PXC describes for your version. In ClickHouse, a table retention period is a TTL; read the current definition first to see the time column and any existing TTL.

```bash
kubectl exec -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 -- clickhouse-client --query "SHOW CREATE TABLE <database>.<table>"
```

> **Warning:** A shorter TTL makes ClickHouse delete slow-query rows older than the new period during background merges; deleted history cannot be recovered. Only when the space is confirmed to be in the slow-query tables listed in step 1 and older history is no longer needed. Rolling back to the previous TTL only keeps future data longer. MySQL PXC is not affected.

```bash
kubectl exec -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 -- clickhouse-client --query \
  "ALTER TABLE <database>.<table> MODIFY TTL <time-column> + INTERVAL <days> DAY"
```

3. Repeat step 1 over the following days. Space is released as old parts are merged away, not at the moment of the change.

## Diagnostic Steps

1. Separate an OOM from a pre-check finding. OOM is a restarting Pod; the pre-check finding is a Service type, even when the Pod is healthy.

```bash
kubectl get pods -n cpaas-system | grep -E 'pxc-ck|ckslow'
kubectl get svc clickhouse-pxc-ck -n cpaas-system
kubectl describe pod -n <namespace> <slowsql-pod> | grep -E 'OOMKilled|Limits|Restart'
```

2. Read the limit actually enforced. Cause 1 applies when the OOM-killed container shows `2Gi` or `2G`. With any other limit, 4Gi is not the fix; size from actual usage and free node memory.

3. Before an uninstall, list the operator subscription and the PVCs so you delete the slow-query volume and not a MySQL PXC volume:

```bash
kubectl get csv,sub,pvc -n cpaas-system | grep -Ei 'clickhouse|pxc-ck|slowsql'
```

High memory without `OOMKilled` while `kubectl get mysql -A` is empty is Cause 4: scale to 0, do not delete the PVC.

4. If the OOM-killed ClickHouse Pod runs in an application namespace and is not the slow-query store, the slow-query causes do not apply. Confirm `OOMKilled` or exit code `137` (a container whose last state is `Error` without `OOMKilled` was not killed for memory, and more memory is not its fix), then raise the memory above the current limit on its `ClickHouseInstallation` as in the Cause 1 resolution, steps 3 and 4. Do not scale it to 0 or delete its PVC for an OOM.

```bash
kubectl get pod -n <namespace> <clickhouse-pod> \
  -o jsonpath='{range .status.containerStatuses[*]}{.name}{" reason="}{.lastState.terminated.reason}{" exit="}{.lastState.terminated.exitCode}{"\n"}{end}'
```

5. Disk growth without OOM or high memory, with `value.bin` files taking the space, is Cause 5:

```bash
kubectl exec -n <namespace> chi-pxc-ck-slowsql-cluster-0-0-0 -- sh -c 'find /var/lib/clickhouse -name value.bin -size +100M | head'
```
