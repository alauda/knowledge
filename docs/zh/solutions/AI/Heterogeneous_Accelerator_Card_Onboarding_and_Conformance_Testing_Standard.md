# 异构加速卡入驻与一致性测试标准

**版本：** v1.0 框架草案 · 征求讨论与确认\
**范围：** 旨在入驻统一计算平台的 GPU 和 NPU 加速卡，包括 NVIDIA、AMD 及国内厂商。\
**当前范围：** 内部应用场景。对外暴露计算能力的场景不在本版本范围内。

## 关于本草案

本草案建立了入驻标准的框架和术语，以供讨论和确认。标记为“待确认”或留空的项目必须在根据第一轮测量和实际场景达成一致后完成。这些项目不是当前的决策标准。

## 1. 范围和一般原则

### 1.1 本文档内容

本文档定义了加速卡入驻统一计算平台时所需的**声明、交付物、测试方法和认证有效期**。

其目的是在入驻之前定义信息边界和验证方法，以便不同厂商的卡片能够一致管理，而不必为每种卡片型号创建单独的流程。

### 1.2 一般原则

1. **使用 Kubernetes 标准机制。** 本版本的基线接口是标准的 **设备插件**，以及 Prometheus 格式的出口。任何专有机制必须解释其与标准机制的关系。
2. **信息必须可收集且语义清晰。** 设备属性、指标和故障信息必须以可收集的形式公开，并指定其定义、单位、分母和采样窗口。语义不清的信息不能纳入统一管理。
3. **按级别分类能力，并按场景使用。** 框架不做“合格/不合格”的二元决策。它对卡片进行能力级别认证，并仅在该级别覆盖的场景中使用。未达到更高级别不妨碍适用场景的入驻。
4. **声明与测量相匹配。** 每个声明必须有相应的验证方法。当声明与测量结果不同时，以测量结果为准，声明必须进行修正。
5. **将认证与版本绑定。** 认证结论适用于确切的版本组合。相关项目在版本变更后必须重新测试；见第 6 节。

### 1.3 责任边界

- **厂商：** 提供设备驱动程序、固件、入驻组件、能力声明、兼容性矩阵和技术支持。
- **平台所有者：** 管理集群侧的部署编排、资源调度、监控聚合、认证级别和使用范围。
- **共同问题：** 涉及设备、驱动程序、运行时和平台组件的问题根据商定的所有权共同调查。
- **认证结论的影响：** 结论代表在**商定的版本组合和测试范围内**的验证结果。这并不意味着产品适用于每个业务场景。

## 2. 入驻接口、分区和能力级别

### 2.1 入驻接口和分区方法

**入驻接口和分区方法是不同的层次，分别描述以避免混淆这两个技术概念。**

#### A. 入驻接口

| 接口               | 位置                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| **设备插件**      | 本版本的**基线入驻接口**。与 Prometheus 格式的出口一起使用，对应于 L0。                                           |
| **DRA**           | 前瞻性的**可选**接口。支持它的厂商可以将其声明为额外能力。                                                          |

**\[DEC]** 支持 Kubernetes DRA 的厂商可以提供 DRA 驱动版本、支持的 Kubernetes 版本、DeviceClass 和 ResourceClaim 示例，以及已知限制。完成附录 A.1。

DRA 支持**不影响本版本的基线入驻或能力认证**。缺乏 DRA 支持不会导致扣分。

仅提供 DRA 而不提供设备插件的实现是否可以被接受为独立的入驻路径，必须由平台根据目标 Kubernetes 版本、DRA 成熟度和项目要求进行评估。目标 Kubernetes 版本**待确认**；见附录 D.1。

#### B. 分区方法

实施方法没有规定，但会影响隔离强度、可实现级别和适用场景：

| 实施方法                                               | 典型隔离强度         | 可实现级别                |
| ------------------------------------------------------ | -------------------- | ------------------------- |
| 硬件分区 / 硬件虚拟化                                  | 通常为硬隔离         | L2-Hard，需测量确认      |
| 原生软件分区                                          | 需测量确认           | L2-Hard 或 L2-Soft       |
| 通过第三方中间件层进行软件拦截                        | 通常为软隔离         | L2-Soft，需测量确认      |
| 无分区支持                                            | —                    | L0 / L1                  |

两个 L2 层级的适用场景在第 2.2 节中定义。**每种方法的最终分类由第 4.2 节的测量结果决定**；此表描述典型情况。

#### C. 公共中间件层

没有原生分区的卡片可以使用公共中间件层，例如 HAMi，以获取分区和基线指标。这是**可选路径，而非入驻要求**。厂商决定是否使用它；不使用它不会影响 L0、L1 或 L3 认证。

相关约束来自于隔离强度，而非路径本身。软隔离不构成故障边界，因此其适用场景遵循第 2.2 节的 L2-Soft 规则。该约束对所有软隔离解决方案同样适用。

### 2.2 能力级别

| 级别                     | 能力                                                                                                                       | 适用场景                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **L0 整卡可用**          | 整卡调度、自动化驱动程序部署和可读的基本健康状态                                                                        | 开发、测试和非关键工作负载                   |
| **L1 可观察**            | L0 加上所有必需的指标、指标与 Pods / Namespaces 的关联和故障报告                                                        | 生产                                          |
| **L2 可分区**            | L1 加上以有限的配置集表示的分区，隔离级别和故障域通过测量确认                                                            | 见下表的层级                                  |
| **L3 可扩展训练**        | L1 加上暴露的互连域和经过验证的多卡和多节点分布式训练                                                                    | 训练和大模型工作负载                         |

**L2 有两个隔离层级。**

| 层级        | 条件                                                                                                                                                                   | 适用场景                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **L2-Hard** | 内存和计算是硬隔离的，**并且**一个实例中的异常不会影响同卡上的其他实例；两个条件均通过测量确认                                                                        | 跨部门共享和生产推理                                                                                      |
| **L2-Soft** | 上述两个条件不均满足                                                                                                                                               | 在一个业务组内的多任务共享和非关键推理；不应在同一卡上混合不同部门的工作负载                              |

L2 和 L3 可以组合，且两者均需先达到 L1。**承载核心业务工作负载的卡片必须达到 L1。如果核心业务使用分区，则卡片必须为 L2-Hard。**

> 故障隔离作为 L2 分层的基础，而不是 L2 入驻要求。将其作为入驻要求会排除所有软件分区解决方案，尽管软分区在一个业务组内共享时可能是合适的。差异通过适用场景而非入驻来处理。

## 3. 基线入驻要求

以下是基线入驻条件。它们与性能或高级能力无关；它们是来自多个厂商的卡片共存于一个可管理平台的前提条件。如果任何项目未满足，则卡片无法以可管理和共存的方式正常入驻。

验证阶段：**材料**是指在材料审查期间检查的；**测量**是指由相应测试组检查的；**端到端**是指在整个评估过程中检查的。

| ID      | 要求                                                                                                                                                                                                                                                                                                     | 验证                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **R1**  | 提供一个容器化的 Kubernetes 设备插件，以 Helm Chart 或 YAML 形式交付。支持 DRA 的实现也可以提供 DRA 驱动和示例；**DRA 支持在本版本中不是基线入驻要求**（见第 2.1A 节）。                                                                                                        | 材料 + T1            |
| **R2**  | 驱动程序安装可以通过 DaemonSet 或自动化脚本自动完成，无需手动维护节点配置。                                                                                                                                                                                                                          | 材料 + T1            |
| **R3**  | 不要求修改或替换集群的默认调度程序。厂商入驻或调度扩展不得影响其他厂商资源的调度。                                                                                                                                                                                                                      | T3                    |
| **R4**  | 建立“设备 → Pod / Namespace”关联。如果指标未直接包含所需标签，请提供可行的关联方法。                                                                                                                                                                                                                  | T4                    |
| **R5**  | 提供涵盖驱动程序、固件、组件、内核、操作系统、Kubernetes 和容器运行时的兼容性矩阵。                                                                                                                                                                                                                      | 材料                 |
| **R6**  | 提供书面的漏洞响应和维护期声明。                                                                                                                                                                                                                                                                      | 材料                 |
| **R7**  | 声明的关键能力与测量结果相匹配。例如，硬隔离声明不得允许跨实例内存访问或在测试中相互影响。                                                                                                                                                                                                             | 端到端               |
| **R8**  | 如果支持分区，请记录资源配置参数、值范围和约束，以便将其打包为有限的可管理资源配置集。如果参数是连续的且无法可靠地打包为固定配置，请记录分配和回收语义。                                                                                                           | 材料（附录 A.2）     |
| **R9**  | 组件所需的主机权限限制在必要范围内，并且每个权限的目的可以解释。                                                                                                                                                                                                                                        | T12                   |
| **R10** | 记录卡片或实例的重置粒度和恢复行为，以及对同一节点上其他设备和主机的影响。**未声明的节点级影响不得发生。**                                                                                                                                                                                        | 材料 + T7a           |
| **R11** | 工作负载容器不得通过设备文件、管理接口或其他方式访问未经授权的设备资源或影响未分配的设备或其他工作负载。如果必须暴露共享控制设备节点，请记录其目的、访问边界和潜在影响。                                                                                                          | T12                   |

## 4. 技术要求

### 4.1 资源暴露和调度语义

- **\[DEC]** 设备插件资源名称或 DeviceClass 名称，以及支持的 Kubernetes 版本范围。
- **\[DEC] 资源配置参数和可分配配置：** 记录配置参数、值范围和约束。提供推荐的可分配配置，以枚举形式列出，包括卡片型号、内存、计算比率、隔离级别、故障域和每张卡的最大实例数。

  平台应将这些打包为有限的、可管理的资源配置集，以便进行配额和分配管理。如果连续参数无法可靠地打包为固定配置，请记录分配和回收语义（对应于 R8）。
- **\[DEC]** 静态属性（模型、内存、每种精度的名义计算和互连带宽）和拓扑属性（NUMA 和互连域）的暴露方法：节点标签、节点注释、设备属性、DRA 属性或出口。说明每个属性的暴露位置。
- **\[DEC] 多厂商共存声明：** 描述任何入驻组件（变更/验证 Webhook）或调度扩展的范围和激活条件。如果没有这样的组件，声明“无”。

  **结果要求（R3）：** 该组件不得无条件拦截与厂商资源无关的对象。

  **所需细节：** 范围和匹配条件、组件不可用时的行为以及对其他厂商资源的影响。平台根据实际影响决定是否接受该组件。

  > 常见的范围限制方法包括 `rules`、`namespaceSelector`、`objectSelector` 和资源名称匹配。如果范围广泛且组件依赖内部逻辑“识别并通过”对象，则该范围内每个对象的创建仍会经过该组件。在这种情况下，`failurePolicy` 和 `timeoutSeconds` 决定组件故障的影响，也应予以声明。
  >
  > 当调度要求可以表示为声明性约束（拓扑亲和性、配置限制或排除规则）时，它们通常比特定厂商的调度器更容易与多个厂商共存。
- **\[DEL]** 每个配置的可运行 YAML 示例：整卡、每个分区配置、独占分配和共享分配。
- **\[TEST]** 使用手动示例启动 Pods，并验证资源可以被请求、设备文件可见且属性可读。验证超请求和重复请求的行为是否符合预期。
- **\[TEST]** 在同一集群中与其他厂商的卡片并行运行。使用其他厂商资源的 Pods 必须正常调度，并且不得被该厂商的组件拦截或重写。
- **\[TEST · 观察]** 在部署该厂商组件之前和之后观察其他厂商 Pods 的调度行为和异常。如果发生明显的拦截、故障或不可接受的性能影响，请根据实际环境确认。此项没有固定阈值。

### 4.2 分区和隔离（L2）

**\[DEC]**

- 分区方法：硬件分区、硬件虚拟化、原生软件分区、通过中间件层的软件拦截或不支持。
- 每个配置的隔离级别：内存隔离（硬/软/无）、计算隔离（硬/软/无）和故障隔离（是/否）。
- **故障域：** 一个实例中的内存溢出、计算死锁或进程故障是否影响同一卡上的其他实例，以及是否可能导致整卡重置或节点故障。
- 是否可以在不重启容器的情况下调整分区，以及在实例销毁后如何清理内存和设备状态。
- 如果支持超分配，请声明最大超分配比例。

**\[TEST]**

| 测试                      | 方法                                                                                             | 决策                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 内存隔离                  | 在一张卡上运行两个实例；一个请求超出其配额的内存。                                               | 超限实例失败，另一个实例不受影响。                                                                                      |
| 计算隔离                  | 在满负载下运行两个实例，配额为半卡。                                                             | 实际份额与配额之间的偏差在商定范围内（参考值 10%，待确认）。                                                            |
| 故障传播                  | 注入内存溢出，强制终止一个进程，或在一个实例中创建无限循环。                                     | 其他实例中的任务继续运行而不受干扰。                                                                                   |
| 分区开销                  | 将使用其全卡配额的一个实例与整卡直通基线进行比较。                                               | 性能损失不超过声明，并保持在商定范围内（参考值 10%，待确认）。                                                         |
| 残留清理                  | 销毁一个实例，创建一个新实例，并检查内存。                                                       | 不会保留上一个实例的数据。                                                                                              |
| 超分配行为                | 如果支持，根据**声明的最大超分配比例**施加负载。                                                | 行为与声明相符，并且不会导致节点级故障。                                                                                |

**分层规则：** 只有当内存和计算隔离均为硬隔离且在故障传播测试中其他实例不受影响时，卡片才为 L2-Hard。否则为 L2-Soft。如果测量结果与声明不符，修正声明并重复受影响的测试。

> 没有定义统一的最小分区粒度。硬件分区通常较粗，但提供更强的隔离；统一的最小值将排除更强的解决方案。粒度由厂商声明，差异通过配置枚举和能力级别处理。
>
> 没有定义超分配的统一上限。此项仅验证声明值的稳定性。

### 4.3 工作负载切换、回收和重置

某些使用模式在不同时间切换工作负载类型，例如交替推理和训练。因此，必须了解工作负载类型之间切换和回收的实际行为。

**\[DEC] 回收和切换**

- 释放先前工作负载后清理内存和设备状态所需的时间。
- 切换工作负载类型是否需要节点重启、驱动程序重新加载或全局分区模式更改；如果是，请记录成本和前提条件。
- 在长时间满负载后接受不同工作负载之前，是否需要设备重置。

**\[DEC] 设备重置语义**

- 重置触发器和**粒度**：整卡重置、实例级重置、驱动程序重新加载或节点重启。
- 重置持续时间以及重置期间卡片是否自动从可分配资源中移除。
- 驱动程序是否必须先解除绑定，以及同一节点上其他卡片上的工作负载是否必须停止。
- **IOMMU 分组：** 卡片是否与节点上的其他设备共享 IOMMU 组；如果是，请描述重置期间的相互影响。
- 重置失败处理：自动重试、故障标记或手动干预。

**\[TEST] T7a 重置影响**（适用于所有卡片；对应于 R10）

在同一节点上其他物理卡片正在提供工作负载时重置目标卡，并验证：

| 检查                                                                      | 决策                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 实际影响与声明相符                                                        | **基线要求。** 未声明的节点级影响，例如主机故障或节点上其他卡片的丢失，不得发生。                                                                                                                                       |
| 其他物理卡上的工作负载继续运行而不受干扰                                  | **生产增强。** 具有此能力的卡片可以与其他工作负载共享节点。没有此能力的卡片根据声明的影响放置在专用节点上，并以限制条件入驻（见第 5.4 节）。                                                                         |
| 重置卡在声明的时间内自动恢复并返回                                        | 与声明进行比较。                                                                                                                                                                                                          |
| 重置期间卡片不被分配新工作负载                                            | 与声明进行比较。                                                                                                                                                                                                          |

此测试必须在隔离测试节点上运行，并且不得与其他测试组共享节点。

**\[TEST] T7b 工作负载切换和回收**（适用于声明支持基于时间的工作负载切换的卡片）

4. 级别分类：
   - L1 需要通过 T4 和 T5。
   - **L2 和 L3 都需要先达到 L1**。L2 还需 T6，并根据其结果分层；L3 还需 T8。
   - T0 和 T7b 不决定能力级别。
5. 结论必须说明**测试的确切版本组合**（驱动程序、固件、组件、操作系统、内核和 Kubernetes）。结论仅适用于该组合。

### 5.4 限制入驻

不满足高级能力要求但具有可接受基线入驻和运行时边界的设备**可以限制入驻**。它不必因单一能力不足而被排除。

| 限制类型        | 示例                                                             |
| ---------------- | ----------------------------------------------------------------- |
| 范围限制        | 特定节点或节点池，特定命名空间                                  |
| 分配限制        | 仅整卡分配；不支持分区                                          |
| 共存限制        | 不允许跨部门共存；不与核心工作负载共存                          |
| 工作负载限制    | 仅指定模型或工作负载类型                                        |
| 操作条件        | 仅在维护窗口中升级；故障后手动恢复                              |

限制必须**在认证结论和平台资源目录中清晰记录**，以便用户在请求容量时了解它们。

> 这种方法将单一能力不足转变为可管理的使用范围，而不是排除设备。

### 5.5 标准计算测量

厂商声称的峰值计算不直接用于比较。厂商使用不同的定义，可能包括或不包括稀疏性，支持不同的精度，并达到不同的利用率水平。因此，跨厂商比较使用共同的测量基础。

- **按工作负载类别分开结果**，而不是使用一个标量：训练吞吐量和推理吞吐量。卡片在这两种工作负载中的排名可能不同。
- 将内存容量、内存带宽、互连带宽和集体通信带宽视为**独立维度**；不要将它们合并为计算指标。
- **单独测量每个分区配置**；不要从整卡性能线性推断分区性能。
- 使用基线卡的测量结果作为参考；基线卡待确认。
- 在主要驱动程序或固件版本变更后重复测量；见第 6 节。

基准集在附录 C 中定义。

### 5.6 阈值确认和激活

为避免在没有测量证据的情况下固定值，首先区分三种不同的事物：

|                       | 状态                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **框架**              | 提议：测试项目、指标类别、级别关系和决策过程。                                                                          |
| **参考值**           | 已提出建议值（15 秒、30 秒、5 分钟、10%、5% 等）；见附录 D.2。                                                          |
| **正式阈值**         | **待确认：** 是否采用建议值以及适用范围；框架的用户确认这一点。                                                          |

阈值分两个阶段生效：

| 阶段                             | 阈值状态                                                                                                                             | 决策方法                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| **第一阶段：基线测量**           | 建议参考值仅用于观察、记录和比较；**不是拒绝标准**。                                                                                | 记录每个测量值及其与参考值的偏差；将结论标记为“第一阶段”。                                       |
| **第二阶段：正式操作**           | 框架的用户确认每个参考值是否成为正式门槛；**不同场景可能使用不同阈值**。                                                            | 确认的阈值成为决策门槛。                                                                            |

在确认后，第一阶段测试的卡片将根据新阈值重新分类。除非触发第 6 节中的重测条件，否则不需要重复测试。

附录 D.2 将阈值分为三种类型，具有不同的确认方法：**政策阈值**取决于用户需求，**能力阈值**需要根据测量进行校准，**方法阈值**由用户根据成本和收益选择。

## 8. 评估和比较

### 8.1 三个步骤

1. 检查**基线入驻要求** R1-R11。
2. 执行 **能力认证**，确定 L0-L3 和隔离级别，并定义适用场景。
3. 对供应商进行 **全面评估** 以进行比较。

### 8.2 评估维度

权重需根据采购策略确认。

| 维度                                                                                     | 权重 | 主要证据                                                                                   |
| ---------------------------------------------------------------------------------------- | ---- | ----------------------------------------------------------------------------------------- |
| 每单位计算的测量性能，具有单独的训练和推理基础                                          |      | T11 测量结果与价格的比率                                                                  |
| 生态系统兼容性                                                                           |      | T10：操作范围、性能成就和数值一致性                                                      |
| 稳定性和故障能力                                                                        |      | T5, T9                                                                                    |
| 操作成熟度                                                                               |      | T1, T7a：自动化、升级和回滚、诊断和重置安全                                              |
| 标准合规性                                                                               |      | Kubernetes 标准机制的采用程度；平台变化越少越好                                          |
| 支持和服务承诺                                                                           |      | 响应时间、维护期和漏洞响应记录                                                            |

> 采购策略决定了训练和推理计算度量的组合方式。本文件未定义单一标量。

### 8.3 处理声明和测量差异

1. 如果 **\[DEC]** 项目与测量结果不同，则更正声明并重复测试。重复的差异必须在评估结论中反映。
2. 如果某项能力仅在已发布的案例中有效，而在等效的补充案例中失败，则根据测量结果重新分类该项目。

> 目的是保持声明与实际行为一致，并根据真实能力分配适用场景。差异并不自动阻止入驻，但会影响级别分类和适用场景。

### C.2 选择原则

1. **至少一个项目必须来自实际业务工作负载**，以便认证结论反映生产行为。
2. **至少一个项目必须是广泛使用的行业模型**，以便结果可以在供应商之间进行比较。
3. **覆盖两个规模：** 一个适合单卡的规模和一个需要多卡协作的规模。
4. **保持引擎中立：** 不要使一个推理引擎成为唯一的先决条件。供应商的专有引擎可以参与，但其接口兼容性必须声明，并且其结果必须与主流引擎的结果分开记录。
5. **仅包括与决策相关的工作负载。** 与实际业务使用无关的工作负载会增加进度而不改变结论。
