# ACP Registry v2 迁移运行手册

本手册将一个 ACP 业务集群从传统图表注册表迁移到由 `cluster-image-registry-operator` 管理的注册表 v2。独立的 `registry-migrate` 工具导入元数据，而注册表 v2 重用相同的 S3 存储桶、端点和前缀。

这些命令不会直接删除镜像或运行 GC。P5 删除传统图表资源及其剩余的 Ingress；P8 中的 `ac delete images` 调用是干运行。切勿添加 `--confirm`。P8 还会恢复记录的 Pruner 暂停状态：如果该状态为 `false`，则可以恢复计划的镜像清理。在批准切换之前确认该行为。

## 阶段概述

| 阶段                  | 目的                                                              | 服务中断 | 失败后重试                               |
| ---------------------- | -------------------------------------------------------------------- | -------- | ----------------------------------------- |
| 0                      | 验证工具、凭证和业务集群上下文                                      | 否       | 是                                       |
| P0 计划                | 生成并审查只读计划                                                 | 否       | 是                                       |
| P1-备份              | 保存资源身份并准备恢复材料                                         | 否       | 是                                       |
| P1-凭证              | 交接拉取凭证                                                       | 否       | 是                                       |
| P2-停止写入者        | 停止传统写入者（**维护窗口开始**）                                 | **是**   | 是                                       |
| P3-最终清单          | 冻结镜像清单和 S3 对象列表                                         | **是**   | 是；记录的保护选择是不可变的           |
| P4-准备操作员        | 将操作员保持在零副本并准备只读配置                                 | **是**   | 是                                       |
| P5-移除传统图表     | 卸载传统插件，然后移除其剩余的 Ingress                              | **是**   | 重试检查；不要重复已完成的卸载         |
| P6-冷导入            | 导入元数据和命名空间限制                                           | **是**   | 是                                       |
| P7-验证              | 恢复操作员并验证只读服务                                           | 读取访问恢复 | 是                                       |
| P8-提交              | 验证业务访问并开启写入（**维护窗口结束**）                         | 恢复     | 首先检查记录的和实时状态               |

使用相同的运行目录进行重试。从第 0 节开始。

## 先决条件

- **工具和恢复程序**：请联系您的 ACP 服务提供商以获取批准的 `registry-migrate` 和兼容的 `ac` 二进制文件、注册表 v2 包以及平台暂停和 S3 恢复程序。
- **命名空间**：默认的操作员安装命名空间为 `image-registry-system`；默认的注册表操作数命名空间为 `cpaas-system`。操作数命名空间在安装时固定。确认实际值并在整个迁移过程中使用 `scope.operandNamespace` 在 `plan.json` 中。
- **存储范围**：如果传统注册表的镜像数据后端使用 PVC 或 HostPath，或者迁移包含非镜像 OCI 工件或非默认 S3 根/前缀，则停止，除非提供商已批准其他程序。仅由节点信任或解析器组件使用的 HostPath 挂载不是镜像数据存储。
- **操作员暂停**：在 P4-P6 期间，操作员必须保持在零副本。手动 InstallPlan 批准不会暂停已运行的操作员。在 P4 之前和移除传统图表之前建立提供商批准的暂停。
- **CLI 兼容性**：`AC_IMAGE_REGISTRY_MODE=legacy/modern` 选择模式，但显式的 `--registry-url` 可以保持请求在注册表 HTTP 兼容路径上。`AC_REGISTRY_COMPAT_OUTPUT` 选择输出合同；在这些检查中保持未设置或设置为 `4.3`。

## 0. 准备终端和工具

使用一个专用的 **Bash** 终端进行所有迁移步骤；在交互式 zsh 会话中不要启用 `set -u`。登录令牌的生命周期取决于平台身份提供者。如果请求返回 `Unauthorized`，请刷新与用于迁移的 kubeconfig 关联的登录。首先列出可用的会话：

```bash
ac config get-sessions
```

在 `CURRENT` 中标记为 `*` 的行是活动会话。使用其 `PLATFORM` 和 `SESSION` 值重新登录：

```bash
printf 'PLATFORM: '; IFS= read -r PLATFORM
printf 'SESSION: '; IFS= read -r SESSION
ac login "$PLATFORM" --name "$SESSION"
```

下面的代码块验证工具和凭证并选择上下文。对于单独的业务 kubeconfig，请在上述登录命令中添加 `--kubeconfig /absolute/path/to/business.kubeconfig`，并在块的 `export KCFG=` 行中使用相同的路径。设置会清除早期的 `KCFG` 值；登录到默认文件不会刷新单独的副本。

```bash
setup_run() {
umask 077
unset KCFG                      # 清除早期终端留下的过时路径
export KCFG="$HOME/.kube/config"
test -f "$KCFG" || { echo "错误：未找到 kubeconfig: $KCFG" >&2; echo "如果业务 kubeconfig 在其他地方，请编辑上面的 KCFG 行" >&2; return 1; }
for b in registry-migrate ac jq curl; do
  command -v "$b" >/dev/null || { echo "错误：未在 PATH 中找到 $b" >&2; return 1; }
done
printf '输入真实的平台管理员账户: '
IFS= read -r ACTOR
test -n "$ACTOR" || { echo "错误：需要管理员账户" >&2; return 1; }
export REGISTRY_NS="cpaas-system"        # 用于首次运行时创建计划；在重运行时由 plan.json 重写
export OPERATOR_NS="image-registry-system"
CTX_LIST="$(ac --kubeconfig "$KCFG" config get-contexts -o name || true)"
test -n "$CTX_LIST" || { echo "错误：$KCFG 中没有上下文" >&2; echo "首先登录: ac login --platform <PLATFORM> --name <SESSION>" >&2; return 1; }
CTX="$(ac --kubeconfig "$KCFG" config current-context 2>/dev/null || true)"
test -n "$CTX" || { test "$(echo "$CTX_LIST" | grep -c .)" -eq 1 && CTX="$CTX_LIST" || {
  echo "可用上下文:" >&2; echo "$CTX_LIST" >&2; printf '输入要使用的上下文: ' >&2; IFS= read -r CTX; }; }
echo "$CTX_LIST" | grep -Fxq "$CTX" || { echo "错误：未找到上下文: $CTX" >&2; return 1; }
ac --kubeconfig "$KCFG" --context "$CTX" whoami >/dev/null 2>&1 || {
  echo "错误：未对上下文 $CTX 进行身份验证（令牌过期？）" >&2
  echo "现有会话:" >&2
  ac --kubeconfig "$KCFG" config get-sessions >&2 || true
  echo "重新登录: ac login --platform <PLATFORM> --name <SESSION>" >&2
  return 1; }
OUT="$PWD/registry-migrate-runs"
if test -n "${RUN_DIR:-}" && ! test -f "$RUN_DIR/plan.json"; then
  echo "警告：忽略过时的 RUN_DIR（没有 plan.json）：$RUN_DIR" >&2
  unset RUN_DIR
fi
if test -n "${RUN_DIR:-}"; then
  test -f "$RUN_DIR/plan.json" || { echo "错误：RUN_DIR 已设置但 plan.json 缺失: $RUN_DIR" >&2; echo "修复：取消设置 RUN_DIR 以开始新的迁移" >&2; return 1; }
  RUN_ID="$(jq -er '.runID' "$RUN_DIR/plan.json")"
  REGISTRY_NS="$(jq -er '.scope.operandNamespace' "$RUN_DIR/plan.json")"
  OPERATOR_NS="$(jq -er '.scope.operatorNamespace' "$RUN_DIR/plan.json")"
  REGISTRY_SERVICE="$(jq -er '.scope.serviceName' "$RUN_DIR/plan.json")"
  REGISTRY_DEPLOY="$(jq -r '.discovery.deployment // empty' "$RUN_DIR/plan.json")"
  GATEWAY_DEPLOY="$(jq -r '.discovery.gatewayDeployment // empty' "$RUN_DIR/plan.json")"
  OUT="$(dirname "$RUN_DIR")"
else
  RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-business-$RANDOM"
  RUN_DIR="$OUT/$RUN_ID"
fi
mkdir -p "$OUT"
S3_ARGS=()
FORCE_ARGS=()
registry-migrate version
ac version --client
printf 'context=%s\nrun-dir=%s\n' "$CTX" "$RUN_DIR"
}
setup_run || echo "停止：第 0 节中止；修复上述错误并重新运行此块。终端保持打开。" >&2
```

确认 `context=` 确定了预期的业务集群。在 P0 之前，使用 `ac --kubeconfig "$KCFG" config use-context "$CTX"` 选择它：`ac` 辅助工具使用 `CTX`，但 `registry-migrate` 使用文件的 `current-context`。

设置会创建 `OUT`；成功的 P0 创建 `$RUN_DIR`。对于重试，恢复原始绝对 `RUN_DIR`（附录 B），然后重新选择所需的 S3、强制、嵌套存储库和 P3 保护选项。不要丢弃有效计划以绕过故障。

下一个代码块定义强制性助手。错误、超时或 `STOP` 消息意味着该步骤需要关注，即使终端保持打开或后续命令打印输出。在进入下一节之前确认阶段的成功检查。

```bash
acn() {
  test -n "${CTX:-}" || { echo "错误：CTX 为空；请先运行第 0 节" >&2; return 1; }
  ac --kubeconfig "${KCFG:-$HOME/.kube/config}" --context "$CTX" "$@"
}
acns() { acn -n "$REGISTRY_NS" "$@"; }
evidence() {
  jq --arg actor "$ACTOR" --arg at "$(date -u +%Y-%m-%dT%H:%M:%SZ)" --arg field "$2" \
    '{version:"v1",runID:.runID,planDigest:.digest,observedAt:$at,actor:$actor,($field):true}' \
    "$RUN_DIR/plan.json" > "$RUN_DIR/$1"
}
stop_deployment() {
  local namespace="$1" name="$2" selector pods
  acn -n "$namespace" get deployment "$name" -o wide || return 1
  selector="$(acn -n "$namespace" get deployment "$name" -o json |
    jq -er '.spec.selector.matchLabels | to_entries | map("\(.key)=\(.value)") | join(",") | select(length > 0)')" || return 1
  acn -n "$namespace" scale deployment "$name" --replicas=0 || return 1
  pods="$(acn -n "$namespace" get pods -l "$selector" -o name)" || return 1
  if test -n "$pods"; then
    acn -n "$namespace" wait --for=delete pod -l "$selector" --timeout=180s || true
  fi
}
```

## 1. P0: 创建并审查计划

```bash
registry-migrate plan --output-dir "$OUT" --run-id "$RUN_ID" \
  --operand-namespace "$REGISTRY_NS" --operator-namespace "$OPERATOR_NS" \
  --kubeconfig "$KCFG" &&
jq -e '(.discovery.blockers // []) | length == 0' "$RUN_DIR/plan.json" &&
REGISTRY_DEPLOY="$(jq -er '.discovery.deployment | select(length > 0)' "$RUN_DIR/plan.json")" &&
GATEWAY_DEPLOY="$(jq -er '.discovery.gatewayDeployment | select(length > 0)' "$RUN_DIR/plan.json")" &&
REGISTRY_SERVICE="$(jq -er '.scope.serviceName' "$RUN_DIR/plan.json")" &&
jq '{scope,storage:.discovery.storage,routes:.discovery.routes,limits:.namespaceLimits,warnings:.discovery.warnings}' "$RUN_DIR/plan.json" &&
echo "P0 OK: $RUN_DIR/plan.json"
```

`P0 OK` 表示计划已生成且阻塞检查通过。如果缺失，请停留在 P0 并检查错误或阻塞：

```bash
jq '.discovery.blockers' "$RUN_DIR/plan.json"
```

计划是只读的。比较范围、S3 存储桶/端点/前缀、原始主机/TLS/IngressClass、副本计数、调度和超时与变更记录和实时集群。任何不匹配时停止。如果 `scope.operandNamespace` 错误，请在再次计划之前在第 0 节中更正 `REGISTRY_NS`。

在停止写入者之前检查是否存在预先存在的注册表 v2 元数据。传统图表测试镜像应推送到传统注册表；请勿手动创建备份的 ImageStream 对象作为迁移测试数据。现有元数据是审查条件，而不是删除它的理由。保存以下列表并检查此迁移所涵盖的存储库中的任何对象：

```bash
check_existing_streams() {
  local crd
  crd="$(acn get crd imagestreams.storage.image.alauda.io --ignore-not-found -o name)" || return 1
  if test -z "$crd"; then
    echo "尚不存在 Registry v2 支持的 ImageStream CRD。"
    return 0
  fi
  acn get imagestreams.storage.image.alauda.io -A -o json \
    > "$RUN_DIR/existing-image-streams.json" || return 1
  jq -r '.items[] | [.metadata.namespace, .metadata.name, .metadata.uid,
    (.metadata.annotations["registry-migrate.run-id"] // "unowned"),
    (.metadata.annotations["registry-migrate.plan-digest"] // "")] | @tsv' \
    "$RUN_DIR/existing-image-streams.json"
}
check_existing_streams_or_stop() {
  check_existing_streams || {
    echo "停止：现有 ImageStream 清单失败；在停止写入者或继续之前修复错误。" >&2
    echo "在清单文件完整之前不要继续到 P1。" >&2
    return 1
  }
}
check_existing_streams_or_stop
```

## 2. P1-备份：保存恢复材料

在 P1-凭证之前完成此阶段，该阶段会在原地重写拉取凭证内容。该工具创建一个经过编辑的注册表范围快照，包含资源身份、所有者、ServiceAccounts、引用和数据摘要。它**不包含**任何凭证数据或 S3 镜像数据。

通过批准的恢复程序单独保留图表版本/值、平台对象和受保护的凭证数据。在恢复材料中保持私密且不被编辑。在删除图表之前确认恢复和保留安排。

```bash
registry-migrate backup --run-dir "$RUN_DIR" --kubeconfig "$KCFG" --approve
```

成功检查：命令以 0 退出并在 `$RUN_DIR` 下写入资源和凭证摘要。在失败时，解决报告的错误并在继续之前重试 P1-备份。

## 3. P1-凭证：交接拉取凭证

保持传统注册表可读。首先暂停管理 `sa-imagepullsecret-controller` 的平台源，以便它无法重新启动控制器。如果发现多个候选项，请使用 `acn get deployments -A -o wide | grep -i imagepull` 确定预期的控制器，然后再继续。

```bash
PULL_SECRET_REF="$(acn get deployments -A -o json | jq -er '
  [.items[] | select((.metadata.name | test("sa-imagepullsecret-controller";"i")) or
    ((.metadata.labels // {}) | tojson | test("sa-imagepullsecret-controller";"i"))) |
    [.metadata.namespace,.metadata.name]] |
  if length == 1 then .[0] | @tsv else error("请检查传统拉取凭证控制器候选项") end')"
PULL_SECRET_NS=""; PULL_SECRET_DEPLOY=""
IFS=$'\t' read -r PULL_SECRET_NS PULL_SECRET_DEPLOY <<< "$PULL_SECRET_REF"
if test -z "$PULL_SECRET_DEPLOY"; then
  echo "停止：无法解析传统拉取凭证控制器；修复上述 jq 错误并重新运行。阶段未记录。" >&2
else
  if test "${#FORCE_ARGS[@]}" -eq 0; then
    stop_deployment "$PULL_SECRET_NS" "$PULL_SECRET_DEPLOY"
  else
    acn -n "$PULL_SECRET_NS" get deployment "$PULL_SECRET_DEPLOY" -o wide
    echo "强制模式：保持传统拉取凭证控制器状态不变"
  fi
  evidence controller-stopped.json legacyControllerStopped
  registry-migrate run --run-dir "$RUN_DIR" --stage P1-凭证 \
    --evidence-file "$RUN_DIR/controller-stopped.json" \
    "${FORCE_ARGS[@]}" --kubeconfig "$KCFG" --approve
fi
```

成功检查：该工具报告凭证计数和 `updated/skipped` 计数，并在日志中记录阶段。现有凭证名称/UID 及其 ServiceAccount 所有者 UID 保持不变。在正常路径中，验证旧控制器已停止，然后再将其停止证据视为有效。暂时不要卸载传统图表。

## 4. P2-停止写入者：停止传统写入者（维护窗口开始）

暂停管理传统图表的平台源。停止注册表和网关部署，暂停传统 Pruner CronJob（如果存在），并停止使用相同 S3 存储桶/前缀的外部作业或元数据写入者。暂停 CronJob 不会停止已激活的 Job。

该块提示缺失的写入者记录字段并创建 `$RUN_DIR/writer-record.txt`；现有的非空 `WRITER_RECORD` 被重用。

```bash
stop_writers() {
export WRITER_RECORD="${WRITER_RECORD:-$RUN_DIR/writer-record.txt}"
if ! test -s "$WRITER_RECORD"; then
  printf '维护窗口开始（RFC3339）：'
  IFS= read -r WINDOW_START || { echo "停止：需要维护窗口开始；未停止任何内容。" >&2; return 1; }
  test -n "$WINDOW_START" || { echo "停止：需要维护窗口开始；未停止任何内容。" >&2; return 1; }
  printf '外部写入者（或无）：'
  IFS= read -r EXTERNAL_WRITERS || { echo "停止：需要外部写入者记录；未停止任何内容。" >&2; return 1; }
  test -n "$EXTERNAL_WRITERS" || { echo "停止：需要外部写入者记录；未停止任何内容。" >&2; return 1; }
  printf '写入者停止时间（RFC3339）：'
  IFS= read -r STOP_TIME || { echo "停止：需要写入者停止时间；未停止任何内容。" >&2; return 1; }
  test -n "$STOP_TIME" || { echo "停止：需要写入者停止时间；未停止任何内容。" >&2; return 1; }
  cat > "$WRITER_RECORD" <<EOF
window_start=$WINDOW_START
external_writers=$EXTERNAL_WRITERS
stop_time=$STOP_TIME
approver=$ACTOR
EOF
fi
if ! test -s "$WRITER_RECORD"; then
  echo "停止：WRITER_RECORD 缺失或为空：$WRITER_RECORD；未停止任何内容。" >&2
  return 1
fi
if test "${#FORCE_ARGS[@]}" -eq 0; then
  stop_deployment "$REGISTRY_NS" "$REGISTRY_DEPLOY"
  stop_deployment "$REGISTRY_NS" "$GATEWAY_DEPLOY"
else
  acns get deployment "$REGISTRY_DEPLOY" "$GATEWAY_DEPLOY" -o wide
  echo "强制模式：保持传统注册表/网关状态不变"
fi
LEGACY_PRUNER="$(acns get cronjob image-pruner --ignore-not-found -o name)"
if test -n "$LEGACY_PRUNER"; then
  if test "${#FORCE_ARGS[@]}" -eq 0; then
    acns patch cronjob image-pruner --type=merge -p '{"spec":{"suspend":true}}'
  else
    echo "强制模式：保持传统 Pruner 状态不变"
  fi
fi
acns get endpoints "$REGISTRY_SERVICE" -o wide
acns get endpointslices.discovery.k8s.io -l "kubernetes.io/service-name=$REGISTRY_SERVICE" -o wide
mkdir -p "$RUN_DIR/verification"
acn get cronjob,job -A -o wide > "$RUN_DIR/verification/legacy-jobs.txt" ||
  echo "警告：无法列出集群作业" >&2
if test "$WRITER_RECORD" != "$RUN_DIR/writer-record.txt"; then
  cp "$WRITER_RECORD" "$RUN_DIR/writer-record.txt"
fi
evidence writers-stopped.json legacyWritersStopped
registry-migrate run --run-dir "$RUN_DIR" --stage P2-停止写入者 \
  --evidence-file "$RUN_DIR/writers-stopped.json" \
  "${FORCE_ARGS[@]}" --kubeconfig "$KCFG" --approve
}
stop_writers
```

正常路径成功检查：旧注册表/网关 Pods 和就绪端点消失，Pruner 被暂停，相关活动作业已完成，阶段被记录。检查 `verification/legacy-jobs.txt` 以获取影响此注册表的作业；与此迁移无关的平台作业不在此范围内。如果列出失败，请在 P3 之前解决该失败。

根据 `WRITER_RECORD` 确认外部写入者。两个未更改的 S3 列表仅是支持观察：相等的对象计数和最新的 `LastModified` 值并不能证明所有写入者已停止或排除覆盖。

如果平台无法保持旧组件停止，则在管理员接受一致性风险后仅使用 `FORCE_ARGS=(--force)`。记录其实际状态和工具的强制警告；不要声称这些 Pods 或端点缺失。请参阅附录 B。

## 5. P3-最终清单：冻结清单和 S3 状态

最终清单记录存储库/标签/摘要关系和清单/配置元数据。`s3-snapshot.json` 是对象列表快照，包含计数、字节和列表摘要；**它不是镜像内容的备份**。层保持在现有的 S3 存储桶/前缀中。

作为恢复点，使用已测试的存储快照或备份。仅启用 S3 版本控制并不是经过验证的恢复证据。如果没有可用的恢复点，请选择显式跳过路径并保留其警告。

## 6. P4-准备操作员：准备只读注册表 v2

在 ACP 控制台中，打开 **管理员 → Marketplace → OperatorHub**，选择目标业务集群，并在 `image-registry-system` 中安装或升级 `cluster-image-registry-operator`。将操作数命名空间设置为 `cpaas-system`（或 `plan.json` 中的命名空间），批准 InstallPlan，并等待 CSV 报告 `Succeeded` 和操作员部署存在。然后在 P4-P6 期间使用经过验证的暂停程序将操作员保持在零副本。

记录原始操作员副本计数以备 P7 使用，与计划的注册表计数分开。P8 恢复 Pruner 基线；新的 ImagePruner 记录 `registry-migrate.original-suspend=false`，允许计划的清理。为了保持清理禁用，请在 P4 之前安排经过批准的暂停基线。之后不要更改记录的注释。

```bash
prepare_operator() {
acn -n "$OPERATOR_NS" get subscription,installplan,csv -o wide || return 1
if ! acn -n "$OPERATOR_NS" get deployment cluster-image-registry-operator -o wide >/dev/null; then
  echo "停止：在 P4 之前安装或升级 cluster-image-registry-operator" >&2
  return 1
fi
stop_deployment "$OPERATOR_NS" cluster-image-registry-operator || return 1
PRUNER="$(acn get imagepruner.imageregistry.operator.alauda.io cluster --ignore-not-found -o name)" || return 1
if test -n "$PRUNER"; then
  acn get "$PRUNER" -o json > "$RUN_DIR/imagepruner-before.json" || return 1
  jq '{annotations:.metadata.annotations,suspend:.spec.suspend}' "$RUN_DIR/imagepruner-before.json" || return 1
  existing_run="$(jq -r '.metadata.annotations["registry-migrate.run-id"] // empty' "$RUN_DIR/imagepruner-before.json")" || return 1
  existing_plan="$(jq -r '.metadata.annotations["registry-migrate.plan-digest"] // empty' "$RUN_DIR/imagepruner-before.json")" || return 1
  current_run="$(jq -er '.runID' "$RUN_DIR/plan.json")" || return 1
  current_plan="$(jq -er '.digest' "$RUN_DIR/plan.json")" || return 1
  if test -n "$existing_run" && test "$existing_run" != "$current_run"; then
    echo "停止：imagepruner 属于运行 $existing_run；拒绝重用" >&2
    return 1
  fi
  if test -n "$existing_plan" && test "$existing_plan" != "$current_plan"; then
    echo "停止：imagepruner 是由不同计划 ($existing_plan) 准备的" >&2
    return 1
  fi
  if test -z "$existing_run"; then
    acn annotate "$PRUNER" "registry-migrate.run-id=$current_run" || return 1
  fi
  if test -z "$existing_plan"; then
    acn annotate "$PRUNER" "registry-migrate.plan-digest=$current_plan" || return 1
  fi
fi
evidence operator-paused.json operatorPaused || return 1
registry-migrate run --run-dir "$RUN_DIR" --stage P4-准备操作员 \
  --evidence-file "$RUN_DIR/operator-paused.json" \
  "${FORCE_ARGS[@]}" --kubeconfig "$KCFG" --approve || return 1
acn get config.imageregistry.operator.alauda.io cluster -o json |
  jq -e '.spec.readOnly == true and
    .spec.imagePullSecret.managementState == "Unmanaged" and
    .spec.storage.managementState == "Unmanaged"' || return 1
acn get imagepruner.imageregistry.operator.alauda.io cluster -o json |
  jq -e '.spec.suspend == true' || return 1
}
prepare_operator
```

成功检查：报告显示 `prepared`；配置具有计划的 S3 设置/路由，`readOnly=true`，拉取凭证/存储管理均为 `Unmanaged`。Pruner 被暂停。如果 ImagePruner 属于另一个运行/计划，则停止；与提供商解决所有权。为 P8 保留 `registry-migrate.original-suspend`。在断言失败后，检查实时配置、CRD 版本和暂停状态，然后重试。

## 7. P5-移除传统图表：卸载传统图表

卸载图表会移除其工作负载；该工具无法自动重新安装它们。首先捕获下面的预卸载凭证列表。在重试卸载后保持此原始基线；之后捕获将隐藏损失。

```bash
date -u > "$RUN_DIR/pre-uninstall-secrets.at"
acns get secret -o name > "$RUN_DIR/pre-uninstall-secrets.txt"
```

在卸载之前，确认平台的保留程序保护原始业务拉取凭证/ServiceAccounts、计划的 Ingress TLS 凭证和 P4 目标 S3 凭证。P4 目标凭证为 `image-registry-private-configuration-user`；保留其 UID 和数据。不同名称的传统源 S3 凭证可能会在建立 P4 目标检查点后与图表一起退役。

然后，管理员通过集群插件页面卸载传统注册表/网关插件。图表拥有的凭证可能会与图表一起删除，因此请立即检查：

```bash
test -s "$RUN_DIR/pre-uninstall-secrets.txt" ||
  echo "停止：预卸载快照缺失；下面的差异无法证明任何内容" >&2
printf '基线捕获时间: %s\n' "$(cat "$RUN_DIR/pre-uninstall-secrets.at" 2>/dev/null || echo unknown)"

```

将仅名称的差异视为初步损失检查。将所需 UID 与计划/P1 记录和 P4 的凭证检查点进行比较。如果缺少或重新创建所需的凭证/ServiceAccount，或目标 S3 凭证发生更改，则停止；使用受保护的恢复材料。重新创建名称不会恢复其 UID。

一旦保留检查通过，移除剩余的 Ingress 并记录 P5。下一个代码块在比较其 UID 后删除计划的 `gateway=true` Ingress；在运行它之前保留路由备份。

```bash
remove_legacy_chart() {
acn -n "$OPERATOR_NS" get deployment cluster-image-registry-operator -o json |
  jq -e '.spec.replicas == 0' >/dev/null ||
  echo "警告：操作员副本不为 0；在移除传统图表之前确认其仍然暂停" >&2
ROUTE_COUNT="$(jq -e '[.discovery.routes[] | select(.gateway == true)] | length' "$RUN_DIR/plan.json")" ||
  { echo "停止：无法从 plan.json 读取路由" >&2; return 1; }
test "$ROUTE_COUNT" -gt 0 ||
  echo "警告：计划没有网关路由；在记录阶段之前确认没有传统 Ingress" >&2
FAILED=""
while IFS=$'\t' read -r name expected_uid; do
  actual_uid="$(acns get ingress "$name" --ignore-not-found -o jsonpath='{.metadata.uid}')"
  if test -z "$actual_uid"; then
    echo "跳过：ingress $name 已经缺失"
    continue
  fi
  if test "$actual_uid" != "$expected_uid"; then
    echo "停止：ingress $name 的 UID 不同 ($actual_uid != $expected_uid)；不删除" >&2
    FAILED=1
    continue
  fi
  acns delete ingress "$name" --wait=true
done < <(jq -r '.discovery.routes[] | select(.gateway == true) | [.name,.ingressUID] | @tsv' "$RUN_DIR/plan.json")
test -z "$FAILED" || { echo "停止：传统 Ingress 清理不完整；阶段未记录。终端保持打开。" >&2; return 1; }
registry-migrate run --run-dir "$RUN_DIR" --stage P5-移除传统图表 \
  --kubeconfig "$KCFG" --approve
}
remove_legacy_chart
```

成功检查：P5 被记录；旧的 Service/Deployments/routes 消失，计划的 TLS 凭证保持不变，业务凭证/ServiceAccount 身份保持不变。遇到 UID 不匹配时停止并咨询提供商。新的 Ingress 使用 `targetName`；旧名称仅为清理目标。

旧网关限制成为每个计划命名空间的 `registry-migrate-image-limits` LimitRange：镜像大小使用 `type: alauda.io/Image` 和 `max.storage`；标签计数使用 `type: alauda.io/ImageStream` 和 `max["alauda.io/repository-tags"]`。传统的 `2GB/2000` 变为 `2Gi/2000`（`2Gi=2048Mi`）。**2000 是该命名空间中每个存储库/ImageStream 的标签限制，而不是命名空间范围的总数。** 计划选择特定于命名空间的规则。迁移不会覆盖用户定义的限制或对未来命名空间应用策略。

## 10. P8-提交：验证业务访问，然后开启写入

### 准备端点和测试镜像

`REGISTRY_URL` 必须是新注册表的外部基本 URL，包括其方案和任何外部端口。默认使用计划的方案和主机名，而不带外部端口。当实际入口点不同时，在运行此块之前设置 `REGISTRY_URL_OVERRIDE`，例如 `https://registry.example.com:11780`。确认该地址提供此注册表。

```bash
P8_ENDPOINT_OK=0
P8_LEGACY_QUERY_OK=0
P8_MODERN_QUERY_OK=0
unset REGISTRY_HOST REGISTRY_SCHEME REGISTRY_URL
REGISTRY_HOST="$(jq -er '
  ([.discovery.routes[] | select(.gateway == true)][0] //
    .discovery.routes[0]).hostname | strings | select(length > 0)
' "$RUN_DIR/plan.json")" &&
REGISTRY_SCHEME="$(jq -er '
  ([.discovery.routes[] | select(.gateway == true)][0] //
    .discovery.routes[0]).scheme // "http"
' "$RUN_DIR/plan.json")" &&
REGISTRY_URL="${REGISTRY_URL_OVERRIDE:-$REGISTRY_SCHEME://$REGISTRY_HOST}" &&
REGISTRY_URL="${REGISTRY_URL%/}" &&
mkdir -p "$RUN_DIR/verification" &&
printf '计划主机=%s\nREGISTRY_URL=%s\n' "$REGISTRY_HOST" "$REGISTRY_URL"
```

预期结果：打印计划的主机和批准的外部 URL。在继续之前解决任何错误或地址不匹配。

对于 HTTPS，颁发者必须受信任，证书 SAN 必须与主机匹配。对于私有 CA，将 `REGISTRY_CA_BUNDLE` 设置为其 PEM 文件；以下代码块将其提供给 curl。`REGISTRY_TLS_INSECURE=1` 仅用于诊断；在接受 TLS 之前重复探测并启用证书验证。

```bash
CURL_TLS_ARGS=()
```

探测端点并在一次请求中保存其响应头：

```bash
   HTTP_STATUS="$(curl -sS "${CURL_TLS_ARGS[@]}" \
     --connect-timeout 10 --max-time 20 -o /dev/null -w '%{http_code}' \
```

预期结果：打印 `注册表可达`，并且块成功退出。匿名的 `200`、`401` 或 `403` 响应仅证明可达性。连接或 TLS 错误会使此检查失败；`502` 或 `504` 通常表示代理或 Ingress 无法访问后端。

### 检查 CLI 兼容性

以现代模式查询集群清单：

预期结果：两个预览都识别批准的标签而不删除它；干运行措辞因 `ac` 版本而异。两个模式都传递 `--registry-url`，因此这些是 HTTP 兼容性检查。P7 单独验证公共镜像 API。失败的检查即使后续块成功也保持未验证。

下一个代码块是**有限凭证格式检查**，而不是对每个命名空间的完整审计。它仅检查 `.dockerconfigjson` 凭证；传统图表拉取凭证通常使用 `.dockercfg`，必须根据 P1 交接记录和原始 SA 引用单独检查。其他注册表的凭证不需要包含此注册表主机。

```bash
acn get secret -A -o json |
  jq -r --arg h "$REGISTRY_HOST" '
    .items[] | select(.type == "kubernetes.io/dockerconfigjson") |
    (.data[".dockerconfigjson"] | @base64d | fromjson? | (.auths // {}) | keys) as $k |
    select(($k | any(test($h))) | not) |
    "审核 \(.metadata.namespace)/\(.metadata.name)：没有 \($h) 的 auth 条目"'
```

没有输出并不证明所有拉取凭证都经过检查或注册表地址完全匹配：该代码块使用正则表达式，而不是精确的主机/端口比较。交叉检查 P1 范围、传统的 `.dockercfg` 对象、每个原始镜像的注册表地址/端口和 SA 引用。另一个注册表的 `REVIEW` 条目并不自动表示迁移失败。

在 P8 之前，拉取凭证管理为 `Unmanaged`，因此操作员**不会自动轮换或修复这些凭证**。在批准交接之前解决缺失条目或无效令牌；不要等待后台刷新。

在提交之前，创建一个一次性 Pod，使用 `imagePullPolicy=Always`，使用批准的迁移测试镜像的**原始地址、ServiceAccount 和拉取凭证**。验证相关业务节点和每个工作负载使用的地址/端口上的实际 kubelet 拉取。记录 Pod、摘要和拉取结果，然后删除测试 Pod。仅 API 查询或现有运行的 Pods 并不能证明新的拉取工作。

在此过程中不要运行 `ac adm prune images` 或 GC。它们需要平台级权限，可能会删除数据。确认记录的 Pruner 暂停值以及计划的清理是否可以在 P8 后恢复。

## 附录 A：已知环境限制

### S3 仅在集群内部可达

如果计划的 S3 端点是集群内部的，则该机器可能无法解析它，P3 可能会停止并显示 `dial tcp: lookup ... no such host`。在 **第二个终端** 中建立端口转发，并保持其在前台。

在该终端中将 `KCFG` 和 `CTX` 设置为迁移终端使用的确切值。其环境是独立的，默认/当前上下文可能标识另一个集群。如果 kubeconfig 没有 `current-context`，请显式提供所选的 `CTX`。将 `minio-system/service/minio` 和端口替换为实际的 S3 服务详细信息：

```bash
: "${KCFG:=$HOME/.kube/config}"
: "${CTX:=$(ac --kubeconfig "$KCFG" config current-context)}"
ac --kubeconfig "$KCFG" --context "$CTX" -n minio-system port-forward service/minio 19000:9000
```

回到 **迁移终端**，确认隧道工作并设置覆盖：

```bash
curl --fail --connect-timeout 5 --max-time 10 http://127.0.0.1:19000/minio/health/live
S3_ARGS=(--s3-endpoint http://127.0.0.1:19000)
```

此覆盖仅更改 P3 的传输地址；在计划/快照中记录的端点和目标配置保持源端点。端口转发不会将 HTTP 转换为 HTTPS。重新建立掉落的隧道并重试相同的运行。

### 身份验证领域和 Ingress 端口不一致

来自 `/v2/` 的 401 响应可能会宣传一个 `WWW-Authenticate` 领域，其端口与外部可达的 Ingress 端口不同，例如 443 而不是 11780。注册表数据在 OCI 身份验证失败时仍然可读。使用第 10 节中定义的 `REGISTRY_URL` 检查挑战：

```bash
curl -sS -k -D - -o /dev/null "$REGISTRY_URL/v2/" | grep -i '^www-authenticate:'
```

将诊断 `-k` 替换为系统信任或 `--cacert /path/to/ca.pem` 以进行验证的 TLS。如果领域无法访问，请使用 curl 诊断，纠正入口点配置并重复 OCI/kubelet 拉取检查。将入口点失败单独记录，而不是元数据完整性；成功的 curl 读取并不建立完整的业务接受。

### 逃生舱口

| 开关                                          | 何时使用                                                     | 效果                                                                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FORCE_ARGS=(--force)`                          | 管理员接受相关的传统组件仍在运行 | 仅绕过传统写入者围栏；API、UID、S3、元数据、阶段和 P4/P6 操作员暂停检查仍然存在。记录强制警告和实际运行状态。 |
| `P3_PROTECTION=(--skip-s3-backup-verification)` | 管理员接受没有建立的 S3 恢复点         | 记录警告和 `not-established`；稍后添加的证明无法更改此运行中的成功 P3。                                                           |

原始的 4.3 `ac` 没有 `set-registry-mode`。使用其显式注册表 URL、kubeconfig 和上下文进行传统查询。单独的兼容性接受记录涵盖其完整的权限/分页矩阵；不要将不同客户端的成功视为原始二进制文件的证明。

### 回滚

`rollback` 在日志中记录 `rollback-requested` 并阻止该运行中的后续阶段推进。**它不执行恢复**：它不会重新安装图表、重新创建原始 UID、删除注册表 v2 资源或恢复 S3 对象。使用报告和以下检查表进行管理员拥有的恢复：

```bash
registry-migrate rollback --run-dir "$RUN_DIR" --kubeconfig "$KCFG" --approve
registry-migrate report --run-dir "$RUN_DIR"
```

- **在图表移除之前**：使用变更记录恢复原始副本、平台/Pruner 状态和图表配置；使用单独保护的材料恢复凭证数据。P1 摘要提供身份证据，而不是凭证内容。
- **在图表移除之后**：首先停止新的注册表写入和协调，然后恢复图表/平台配置、凭证和 S3 访问，通过批准的恢复程序。
- **在 P8 之后**：还要考虑新镜像和令牌轮换。不要在没有协调恢复边界的情况下重新激活传统 S3 写入者。
- **在恢复之后**：创建一个新的运行 ID。不要编辑旧计划/日志以绕过身份漂移。

该工具在一个运行中是幂等的：已完成的工作会被跳过或重新验证。保留计划、日志、备份摘要、清单、快照、证据、验证输出和单独的恢复材料。
